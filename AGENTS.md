# URL-Shortener Agent Guide

## Build & Run
- **Java 25**, **Spring Boot 4.1.2**, **Maven**. No Gradle artifacts.
- `.mvn/wrapper/` exists but `mvnw` is missing — use system `mvn`.
- Entry point: `cc.hrva.urlshortener.UrlShortenerApplication`
- Local dev:
  ```bash
  # Start backing services first
  docker compose -f docker/docker-compose.yml up
  # Then run the app with local profile
  mvn spring-boot:run -Dspring-boot.run.profiles=local
  ```
- MCP end-to-end check on its own throwaway containers: `scripts/mcp-e2e.sh` (see MCP connector)
- Build: `mvn clean package` → output in `target/`
- Docker: `Dockerfile` copies `target/*.jar`, multi-arch CI build; runs with `-XX:MaxRAMPercentage=75` (the JVM default is 25 % of the container limit), as a blocklist refresh holds up to millions of entries in memory

## Local Dev Users
`LocalDataInitializer` (only with `local` profile) bootstraps two email-verified local accounts:

| Email | Password | Role | Slots |
|-------|----------|------|-------|
| `admin@localhost` | `admin123` | ROLE_ADMIN | 10 |
| `user@localhost` | `user123` | ROLE_USER | 4 |

Idempotent — safe on restart. Liquibase seeds `ROLE_USER` and `ROLE_ADMIN` authorities.

## Local Dependencies
- **Postgres** (`localhost:5432`, `root:root`, db `url_shortener`)
- **Redis** (`localhost:6379` — overridden in `application-local.yaml`, no longer needed to set manually), 6.2 or newer
- **MailHog** (`localhost:8025`, SMTP on `localhost:1025`)
- The app downloads the enabled blocklist sources into Redis at startup (each source's `memoryBytes` shows the cost) and needs outbound https for them, RDAP and the redirect checks.

## End-to-end check of the link checks
No test boots the whole app, so check it by hand on a throwaway Postgres 18 and Redis 8 without Docker (Homebrew binaries; any free ports, kept off 5432, 6379 and 8080):
```bash

redis-server --port 56379 --bind 127.0.0.1 --save '' --appendonly no --daemonize yes --logfile "$E2E/redis.log"
mvn -q -DskipTests package && cp target/url-shortener-*.jar "$E2E/app.jar"
java -jar "$E2E/app.jar" --spring.profiles.active=local --server.port=18080 \
  --spring.datasource.url=jdbc:postgresql://127.0.0.1:55432/url_shortener --spring.datasource.username=e2e --spring.datasource.password= \
  --spring.data.redis.port=56379 --app.mcp.issuer=http://localhost:18080 \
  --spring.security.oauth2.client.registration.google.client-id=dummy --spring.security.oauth2.client.registration.google.client-secret=dummy
```
- Sign in as `admin@localhost` / `admin123` (`POST /api/v1/auth/login`) for the admin endpoints; `GET /api/v1/admin/blocklist-sources` shows each source's download.
- Send `CF-Connecting-IP: <ip>` to act as different visitors: every anonymous create counts toward that network's 10 per hour, refusals included.
- Run the jar from a copy, so `mvn clean` doesn't pull it from under the running app.

## API Patterns
- **Plural resource names**: `/api/v1/urls`, `/api/v1/api-keys`, `/api/v1/users`, `/api/v1/auth`
- **Proper HTTP methods**: `POST` for create, `DELETE` for delete, `PATCH` for state changes, `GET` for reads
- **API keys in header**: `X-Api-Key` header (NOT in URL path)
- **Pagination**: `@PageableDefault(size=20)` on all list endpoints — pass `?page=0&size=20` query params
- **Response DTOs**: Controllers return `UrlResponse`, `ApiKeyResponse`, `UserDto`, `AdminUserResponse` — NOT JPA entities directly. Build the DTO inside the service's transaction and copy every lazy collection into it (`AdminUserResponse.from` and `UserToUserDtoConverter` take `List.copyOf` of the roles), so it serialises after the transaction (open-in-view is off, see Database). `PATCH /users/password` and `POST /auth/password-reset/confirm` still return the `User` entity (its `authorities` come loaded through `findByEmail`'s `@EntityGraph`).
- **Update converters build a copy**: `UrlUpdateDtoToUrlConverter`, `UserUpdateDtoToUserConverter` and `ApiKeyUpdateDtoToApiKeyConverter` load the row and return a new entity carrying only the id and the editable fields with the request applied; they never modify the entity they load. The service copies those fields onto the row it loaded in its write transaction and saves that row, never the copy (it has no password, roles, key or owner). Never modify an entity loaded outside its write transaction (see Database); before v2.8.3, with open-in-view still on, a refused link edit was saved that way by the audit row's flush.
- **Case conversion**: always `toLowerCase(Locale.ROOT)` / `toUpperCase(Locale.ROOT)`, never the no-argument forms, which follow the server's locale (under `tr-TR` an `I` lower-cases to `ı` and an `i` upper-cases to `İ`, so a typed TOTP secret, a tag or a bot-probe path would stop matching). Turkish-locale tests cover `Totp`, `TagNormalizer`, `UrlSpecification.hasTag`, the bot-probe check in `DefaultUrlService`, `LowerCaseClassNameResolver` and `LikePatterns`; SQL `lower()` is the database's.
- **Error format**: `{"error": "message"}` via `GlobalExceptionHandler` (`@ControllerAdvice`)
- **Exception → HTTP status mapping**: `UserNotFoundException`/`ApiKeyNotFoundException`/`BlocklistSourceNotFoundException`/`DomainRuleNotFoundException`/`ReservedAliasNotFoundException`/`BioPageNotFoundException` → 404, `EmailExistsException`/`ShortUrlAlreadyExistsException`/`BioHandleUnavailableException`/`BioPageConflictException`/`ApiKeyActiveException` → 409, `NoAuthorizationException` → 403, `BadCredentialsException` → 401, `RateLimitExceededException` → 429, a malformed body, a mistyped or missing parameter → 400 (an unknown enum value in a body names the allowed ones: `{"error": "Action must be OK, TRUST_DOMAIN, BLOCK_LINK, BLOCK_DOMAIN or BLOCK_USER"}`; enums are read by name only, never by number), an unsupported media type → 415, `CommonException` (catch-all for all custom exceptions not handled above) → 400, everything else → 500.
- **Validation errors**: Return `{"field": "message"}` map on 400. That covers a body (`MethodArgumentNotValidException`) and the items of a list body such as `/urls/bulk` (`HandlerMethodValidationException`, which would otherwise be a 500); an invalid item refuses the whole request before any link is created.
- **Destination length**: at most 2048 characters (`UrlValidator.MAX_LONG_URL_LENGTH`). `@Size` on `CreateUrlDto.longUrl` and `UrlUpdateDto.longUrl` answers 400 `{"longUrl": "Destination URL must be 2048 characters or fewer"}`; `checkIfLongUrlIsValid` checks the same limit first (on create after `CreateUrlToUrlConverter` has put `https://` before a scheme-less destination, so 2041–2048 characters without a scheme pass `@Size` and fail here), so an overlong destination (`{"error": …}`) never reaches the shortener, blocklist or Safe Browsing checks. The `URL.LONG_URL` column is `VARCHAR(2048)` since 027.

## Key Endpoints
| Method | Path | Auth | Notes |
|--------|------|------|-------|
| POST | `/api/v1/urls` | Optional `X-Api-Key` | Create short URL. Optional `domain` (a hostname, at most 253 characters, also per item on `/urls/bulk` and with an API key): the caller's own `ACTIVE` domain as an active account, else 400 `{"domain": "Choose one of your active domains, or leave it empty for hrva.cc."}` (anonymous callers too); null or blank means hrva.cc. Aliases are unique per domain (see Custom domains) |
| GET | `/api/v1/urls/{short}` | None | Redirect info (records a click (bots are counted separately and refused on visit-limited links); a `qr` query parameter makes it a QR scan, see Click analytics) |
| GET | `/api/v1/urls/{short}/peek` | None | Quick peek (longUrl, shortUrl, createDate) |
| GET | `/api/v1/urls/{short}/preview` | None | Rich preview (title, description, og:image) |
| GET | `/api/v1/urls/{short}/qr` | None | QR code PNG (`?size=300`) of `<app.server-url>/<alias>?qr`, so its scans count as QR scans; `https://<hostname>/<alias>?qr` for a link on a custom domain |
| GET / POST | `/api/v1/urls/{short}`, `/peek`, `/preview`, `/qr`, `POST /unlock` with `?domain=` | None | The same public lookups for a link on a custom domain (a hostname, normalised like an application). Without `domain` they mean hrva.cc. A hostname that isn't an `ACTIVE` domain with an active owner → 404 `URL doesn't exist`, the same as an unknown alias |

## SSO (OAuth2)
- Google and GitHub OAuth2 login supported via `spring-boot-starter-oauth2-client`. GitHub is offered only while `OAUTH2_GITHUB_CLIENT_ID` is set.
- **Login flow**: Frontend links to `/oauth2/authorization/google` (or `/github`). Backend handles callback, creates/finds user by email, issues JWT, redirects to `{frontendUrl}/auth/callback?token=...`. With two-step verification on it issues no JWT: it redirects to `{frontendUrl}/auth/callback?pendingToken=<token>&methods=TOTP,WEBAUTHN,RECOVERY_CODE` (the methods the account has, comma-joined, possibly empty), and the frontend finishes it like a password sign-in's second step. Other outcomes: `?error=google_email_unverified`, `?error=github_email_unverified`, `?error=no_email`, `?error=invalid_email`, `?error=registration_disabled`, `?error=account_inactive`, `?error=two_step_unavailable` (Redis down). Anything that fails the OAuth flow itself (consent cancelled, a failed token, user-info or GitHub emails call) goes through `OAuth2LoginFailureHandler` to `?error=provider_error`; only the error code is logged (anything outside `[A-Za-z0-9_]` becomes `_`, capped at 64 characters, so `?error=` can't forge a log line), never the provider's description.
- **Registrations** (`OAuth2ClientConfiguration`, which defines the `ClientRegistrationRepository`): Google comes from `spring.security.oauth2.client.registration.google` through Boot's own `OAuth2ClientPropertiesMapper`, so it is registered exactly as Boot would, and Boot still refuses to start with an empty `OAUTH2_GOOGLE_CLIENT_ID`. GitHub comes from `app.github-sign-in` (`client-id: ${OAUTH2_GITHUB_CLIENT_ID:}`, `client-secret: ${OAUTH2_GITHUB_CLIENT_SECRET:}`, `scope: user:email`, `redirect-uri: https://hrva.cc/login/oauth2/code/github`, GitHub's endpoints from `CommonOAuth2Provider.GITHUB`) and is added only when the client id has text. Never put GitHub under `spring.security.oauth2.client.registration`: Boot's `OAuth2ClientProperties` refuses a registration with an empty client id at startup ("Client id of registration 'github' must not be empty."), and the security tests that `@Import(SecurityConfiguration.class)` without `OAuth2ClientConfiguration` would bind it too. Those tests keep Boot's own repository from their google test properties. `OAuth2ClientConfigurationTest` loads the real `application.yaml`.
- **Verified email only.** `SecurityConfiguration` wires `OAuth2LoginUserService` into `oauth2Login` explicitly (`userInfoEndpoint(...).userService(...)`), so another user service bean in the context changes nothing (`OAuth2LoginFlowTest` keeps a `@Primary` decoy to prove it). The security tests that import `SecurityConfiguration` mock it next to the success handler. Its provider calls (`/user`, Google's userinfo, GitHub's emails) share a JDK request factory with a 5 s connect and 10 s read timeout; the user-info `RestTemplate` keeps Spring's `OAuth2ErrorResponseErrorHandler`. Google's user info passes through unchanged. For GitHub it always reads `GET https://api.github.com/user/emails?per_page=100` with the access token (`/user`'s `email` is the public one and says nothing about verification), puts the entry that is both `primary` and `verified` in `email`, drops `/user`'s `email` when there is none, and sets `email_verified` to whether there was one. A failed emails request fails the sign-in as `invalid_user_info_response`.
- `OAuth2LoginSuccessHandler` refuses every sign-in whose `email_verified` isn't true (`true` or `"true"`) before it looks up any account: `?error=github_email_unverified` for GitHub, `?error=google_email_unverified` otherwise. An unverified address never signs in or attaches to an existing account, and a GitHub sign-in that skipped `OAuth2LoginUserService` is refused rather than trusted.
- **Unconfirmed accounts**: when a sign-in lands on an active account whose `emailVerified` isn't true (someone signed up with that address and a password but never confirmed it), the handler first replaces the password with a random value that is no BCrypt hash, so no password can match it, and only then marks the email confirmed, in one targeted update (`UserRepository.confirmEmailAndReplacePassword`, which only touches a still-unconfirmed row, clears the persistence context, and is logged only when it changed the row). Never just flip the flag: that would hand a password someone else chose for the owner's address a confirmed account. An inactive account is refused untouched. `OAuth2SignInWritesTest` checks the row.
- **Paused sign-ups**: with `app.registration-enabled: false`, a Google or GitHub sign-in to an existing account still works; one that would create an account goes to `?error=registration_disabled` (the frontend shows email sign-up's text, "Registrations are currently disabled"), with nothing saved and no sign-up alert.
- `OAuth2LoginSuccessHandler` gets only `PendingLoginStore` and `TwoStepMethods` for the second step: `SecurityConfiguration` constructor-injects the handler and also declares `PasswordEncoder`, so anything that reaches `PasswordEncoder` (`TwoFactorService`, `UserService`, `SignInService`) would make the context cycle.
- **OAuth2 users** get `authProvider = "google"` or `"github"` on the User record. Their email cannot be changed (blocked at service level).
- Configured via `application-oauth.yaml` (gitignored) or environment variables for production: `OAUTH2_GOOGLE_CLIENT_ID`, `OAUTH2_GOOGLE_CLIENT_SECRET`, `OAUTH2_GITHUB_CLIENT_ID`, `OAUTH2_GITHUB_CLIENT_SECRET`.
- OAuth2 client secrets for local dev go in `application-oauth.yaml` (excluded from git via `.gitignore`). GitHub's go under `app.github-sign-in` there, with `redirect-uri: http://localhost:8080/login/oauth2/code/github` to match a local GitHub OAuth app.
- The GitHub OAuth app (github.com → Settings → Developer settings → OAuth Apps): homepage `https://app.hrva.cc`, authorization callback `https://hrva.cc/login/oauth2/code/github`.

## Database
- **Liquibase** root: `src/main/resources/db/dbchangelog.xml`
- Migrations auto-run on startup. Codebook seeds ROLE_USER(id=1) and ROLE_ADMIN(id=2).
- User accounts have `AUTH_PROVIDER` column — `"local"` for email/password users, `"google"`/`"github"` for SSO.
- **Open-in-view is off** (`spring.jpa.open-in-view: false` in `application.yaml`; `OpenInViewTest` checks there is no `OpenEntityManagerInViewInterceptor` and no startup warning). A request has no `EntityManager` of its own: each `@Transactional` call gets one for its transaction, and the entities it returns are detached once it ends. So in new code:
  - load what you read inside the transaction: fetch a lazy association with the entity (`UserRepository.findByEmail` and `ApiKeyRepository.findApiKeyByKey` fetch the roles with an `@EntityGraph`), or read it before the transaction ends. A lazy read after it is a `LazyInitializationException`, a 500. The lazy associations are `User.authorities`, `User.apiKeys`, `User.urls`, `BioPage.owner`, `BioPageButton.page` and `.url`, `BioHandleHold.page` and `PasskeyCredential.user`; every other `@ManyToOne` and `Url.tags` are eager.
  - return DTOs built inside the service's transaction, with every lazy collection copied (`AdminUserResponse.from` and `UserToUserDtoConverter` take `List.copyOf` of the roles).
  - compare entities by id, never with `equals` or `==`: `User`, `Url` and the other entities have no `equals` (only the `Authorities` codebook has one, from `@Data`), and two loads in different transactions are two instances (`verifyUserAdminOrOwner` in both validators compares ids).
  - never modify an entity loaded outside the write transaction: saving it is a `merge` that writes back every stale field. Re-read the row in the write transaction and apply the change there, or write it with a targeted update (`UserRepository.deactivateById` and `reactivateById` for an admin block or reactivation and for `active` in the admin user edit, `UserRepository.recordLastLogin` for a Google or GitHub sign-in, `ApiKeyRepository.recordUse` for a key's use, `ApiKeyRepository.deactivateActiveByOwnerId` for a deactivated user's keys). `User`, `BlocklistSource`, `BioPageReview`, `ApiKey` and `Url` are `@DynamicUpdate`, which keeps a save of a row loaded in the same transaction to the columns it changed: a key's revoke, activation or admin edit writes only those columns, so a use counted meanwhile stays (`ApiKeyWritesTest`), and a link's revoke, edit, reactivation or block likewise keeps a click, `lastAccessed` or a visit-limit stop recorded after the re-read (`UrlWritesTest`). Neither has a `@Version`, and nothing relies on a full-row write (every `save` of either is of a row loaded in its own write transaction). It doesn't help a `merge`: the merge reads the row as it is now and copies the stale fields over it, so every column changed meanwhile looks dirty and is written back (`ModerationUserWritesTest` caught `last_login` and `password` reverted this way before the targeted updates).
  - `entityManager.detach` has nothing to detach: no method holds a persistence context across transactions, so don't add one before a re-read.
  - this holds everywhere: filters (`JwtFilter`, `OAuth2LoginSuccessHandler`), `@Async` methods and scheduled jobs never had a request `EntityManager`; controllers and the MCP tools (served through Spring MVC) had one until open-in-view was turned off in v2.13.1.

## Performance
- **Redis caching**: `@Cacheable("urls")` on URL lookup (`peekUrlByShortUrl` only). 1-hour TTL. `@CacheEvict` on mutations.
- **Graceful degradation**: `CacheErrorHandler` logs and falls through to DB when Redis is down — no 500s.
- **Redis fails fast**: Lettuce rejects commands while its connection is down (`RedisClientConfiguration`: `REJECT_COMMANDS`, auto-reconnect kept), so a dropped Redis fails each call at once; `spring.data.redis.timeout: 3s` only bounds a hung Redis. Every Redis caller must therefore stay fail-soft, catching the failure and degrading on purpose (cache → database, click-time blocklist check → let the visitor through, `/unlock` rate limit → allow, unique visitor check → a new visitor, burst check → no alert, public numbers → computed and allowed). Only the documented rate limits under MCP connector and the sign-in state under Passkeys fail closed: the pending two-step sign-in, passkey ceremonies and the passkey options limits answer 503, because no JWT may be issued without the second step. The weekly digest's once-a-week claim is the other deliberate exception: with Redis down it skips the week rather than risk a double post (see Weekly digest). A password sign-in without two-step verification never touches Redis.
- **Read-only transactions**: `@Transactional(readOnly = true)` at class level on all services, overridden with `@Transactional` on write methods.
- **SafeBrowsing client**: Singleton bean (not built per-request). Graceful degradation on API error (returns `List.of()`).

## Security
- JWT in `Authorization: Bearer` header. Stateless sessions on the API chain; the MCP authorization server chain keeps a short HTTP session for the login bridge (see MCP connector).
- Login rate limiting: Guava cache, 20 attempts/day per IP, 1-day expiry. Wrong 2FA codes also count per account (`2fa:<userId>` key) and stop further checks once the limit is hit. Failed passwordless and second-step attempts (expired sign-ins and ceremonies, refused passkeys, wrong codes) count against the same per-IP budget, so password and passkey failures from one client share it; second-step failures, and wrong codes or refused passkeys when turning two-step off or removing the authenticator app, also count on `2fa:<userId>`. The sign-in endpoints (`/login`, `/auth/2fa/totp`, `/auth/2fa/webauthn/options` and `/verify`, `/auth/passkeys/verify`) first refuse a blocked network with 403 `Too many failed sign-ins from this network. Try again tomorrow.` (`LoginAttemptService.NETWORK_BLOCKED`, the only producer of that text); `/auth/passkeys/options` has only its own per-network limit. A locked account (`2fa:<userId>` at the limit) gets 403 at the second step and on the legacy `/login` `code` (`TwoStepLockMessage`): `Too many wrong codes for this account. Try again in 24 hours, or sign in with a passkey.` when it has at least one passkey known to sign in alone (`SYNCED` or `DEVICE_BOUND`; an `UNKNOWN` kind may not, so it gets the short text; a passwordless passkey sign-in checks only the network, never `2fa:<userId>`), otherwise `Too many wrong codes for this account. Try again in 24 hours.` The second step checks the lock before it counts an attempt on the pending token, and a wrong code or refused passkey that takes the account to the limit answers with that lock text, not the tries left or the out-of-attempts 410. The two-step settings endpoints (turning off, removing the authenticator app) have no per-IP check; they count on `2fa:<userId>` only, and always use the text without the passkey clause, as turning off with a passkey is locked too. The 24 hours are the cache's 1-day `expireAfterWrite`: a blocked key takes no further writes, so it clears a day after the failure that locked it.
- Re-auth password counter: every password check of `Reauthentication.confirmPassword` (passkey registration options and removal, `DELETE /users/me`, `PATCH /users/password`) counts wrong passwords on `reauth:<userId>` in the same in-memory `LoginAttemptService`; at the limit (20) it answers 403 `Too many wrong passwords. Try again in 24 hours.` before comparing, and a right password or a successful password reset by email clears the key. A blank password → 400 `Enter your current password.` and isn't counted.
- Public lookups (`GET /urls/{short}`, `/peek`, `/preview`, `/qr`) never return the owner's email or tags; a password-protected link's destination is left out (no preview fetched, no click recorded) until `/unlock`. `/qr` encodes the short link with the QR marker (`app.server-url` + alias + `?qr`), size clamped to 64–1024.
- `/api/v1/public/**` is open to everyone, every method (one `permitAll` matcher): the public bio page read and its view beacon. `/@{handle}` falls under the existing `/*` rule.
- `/unlock` is rate limited through `RedisFixedWindowRateLimiter` (`service/ratelimit/`): 10 attempts per client network and 50 per link per 15 minutes (allowed if Redis is down).
- Link creation is rate limited in `DefaultUrlService` through `RedisFixedWindowRateLimiter` (`service/ratelimit/`), per hour: 10 links per client network without an account (`create:anon`, IP from `ClientIpResolver` in `UrlController`), 60 per account with one (`create:user:<id>`, shared by the web, API keys and the signed-in MCP `shorten_url`). Admins are exempt and each link of `/urls/bulk` counts. Over the limit → 429 `"You've created a lot of links in a short time. Try again in an hour."` Allowed if Redis is down. Cheap refusals come first, so junk can't trigger the slow link check: an API key is checked (unknown, expired, revoked, over its limit) → the create rate limit → the anonymous-disabled refusal → the URL checks (`validateUrl`, the 2048-character limit first; up to a few seconds on a cold RDAP or Spamhaus cache) → the write transaction, where an API key's use is recorded and a lost alias race becomes a 409 (see Unique short URLs). The use is the transaction's first statement, one guarded update (`ApiKeyRepository.recordUse`: `apiCallsUsed + 1`, and `active` off when that reaches `apiCallsLimit` or `expirationDate` has passed, `where active = true`), never a save of the key loaded before the checks; its row lock makes concurrent creates with one key count one after the other. When it changes no row (the key was revoked or used up during the checks) the create is refused like an inactive key, 400 `API key is invalid`, before anything is inserted or cached; a lost alias race rolls the use back with the link. `RateLimitExceededException` is a 429 everywhere, `/unlock` included.
- A failed limiter check (Redis down) logs one `Rate limit check failed exception=<class>` in `RedisFixedWindowRateLimiter` (never the IP, key or Redis host) and throws `RateLimiterUnavailableException`; each caller then logs what it did. Allowing: `Create rate limit unavailable, allowing the link`, `Unlock rate limit unavailable, allowing the attempt`, `Report rate limit unavailable, allowing the report`, `Public stats rate limit unavailable, allowing the request`. Refusing with 503: `Client registration refused because the rate limiter is unavailable`, `Passkey options refused, rate limiter unavailable name=<passkey-options or passkey-second-step-options>`, `Second step refused, attempt counter unavailable user id=<id>` (never the pending token).
- Link previews only fetch public addresses: loopback, private, link-local, CGNAT and ULA targets are refused, and each redirect hop (max 3) is re-checked.
- New passwords need at least 8 characters (register, reset, change). `User.password` is `@JsonIgnore`d.
- An email address must pass `User.email`'s own checks (`@Email`, which caps the local part at 64 characters, and `@Size(max = 255)`, the column's length) before anything is saved or sent: `UserRegisterDto` and `UserUpdateDto` (an admin's email change) carry the same two, so registration answers 400 `{"email": "Enter a valid email address (e.g. you@example.com)"}` or `{"email": "Email must be 255 characters or fewer"}`. A Google or GitHub sign-up whose address fails them (checked with the `Validator` against `User.email`) is sent to `{frontendUrl}/auth/callback?error=invalid_email`, which the frontend shows with its own message.
- Direct `Cache` calls in `DefaultUrlService` go through `getFromCache`/`putInCache`/`evictFromCache`, which log and fall back to the database when Redis fails; a unique visit that reaches the limit evicts the cached entry (`DefaultClickAnalyticsService`, see Click analytics).
- CORS via `CorsConfigurationSource` bean (not headers in JwtFilter). Allowed: frontend origin + all standard methods.
- Client IP resolved via `ClientIpResolver` (never read X-Forwarded-For manually): a single `CF-Connecting-IP` header that parses as an IP literal wins (set by Cloudflare; trustworthy only while the origin accepts traffic from Cloudflare alone), otherwise `request.getRemoteAddr()` as rewritten by `ForwardedHeaderFilter`. `ForwardedHeaderFilter` runs after the Spring Security chains, so filters inside them see the proxy address unless `CF-Connecting-IP` is present.
- Logging: SLF4J via `@Slf4j`, parameterized `{}` format. Sign-in, OAuth and email log lines mask addresses with `EmailAddresses.masked` (`r***@gmail.com`) and add the user id. Never log a pending token, ceremony id, challenge, code, password, public key or user handle; a passkey's credential id appears only as its first 8 characters (`credential=AbCdEfGh…`).
- Actuator endpoints: `/actuator/health` public, all others ROLE_ADMIN only.
- **Unsubscribe** (`UnsubscribeController.UNSUBSCRIBE_ENDPOINT`, GET and POST) is `permitAll` next to the reports rule; everything else under `/api/v1/notifications/**` would need a token. A stale JWT on it is ignored.
- **Channel posts** go through `PublicHttpFetcher.post`: https only, public addresses only (resolved again right before the request), never a redirect (a 3xx is a failed delivery), 10 s timeout. Destination probes (`PublicHttpFetcher.probe`) take http or https and follow at most 5 hops, each resolved and checked again. `DiscordWebhookClient` stays the owner's `DISCORD_WEBHOOK_URL` only and is never handed a user's URL.
- **Login gating** (in order): password auth → `emailVerified` check (`EmailNotVerifiedException` → 403) → if `twoStepEnabled`, no token: `{twoStepRequired: true, twoFactorRequired: true, pendingToken, methods}` (`methods` from `TwoStepMethods`: `TOTP` when an authenticator app is set up, `WEBAUTHN` with at least one passkey, `RECOVERY_CODE` with an unused code). The client finishes with `POST /auth/2fa/totp` or the `/auth/2fa/webauthn` pair. `active` enforced at `UserDetails.enabled` (password) + `OAuth2LoginSuccessHandler` + per-request in `JwtFilter`.
  - **Pending token** (`RedisPendingLoginStore`): 32 random bytes, base64url, in `auth:pending-login:<token>` → `{"userId":42,"rememberMe":true}` for 5 minutes, at most 5 attempts (`rate-limit:pending-login:<token>`, counted with `RateLimiter.increment`, which returns the window's count; options requests don't count), consumed once with `GETDEL` on success. A wrong code with 2 or fewer attempts left → 401 `Invalid two-factor code. 2 tries left.` or `Invalid two-factor code. 1 try left.` (otherwise `Invalid two-factor code`); a refused passkey at the second step gets the same suffix after its own text (`That passkey or security key couldn't be verified. Try again. 2 tries left.`). The fifth failure discards the token → 410 `Too many wrong codes. Sign in again to get 5 more tries.` (a sixth call that races in before the discard gets the same; a later one finds no token and gets the expiry 410) (unless that failure locked the account: then the 403 lock text, see Security). Unknown, expired or used → 410 `Your sign-in expired. Sign in again.`; Redis down → 503 `Two-step sign-in isn't available right now. Try again in a minute.`
  - **Google and GitHub** go through the same second step: the callback redirects with `pendingToken` and `methods` (see SSO).
  - **A passwordless passkey sign-in** (user verification required) skips the second step: it is already two factors.
  - Every sign-in builds its JWT in `SignInService.signIn` from the user's stored authorities (password login no longer uses the `AuthenticationManager` result), and records `lastLogin`. A Google or GitHub sign-in records it in `OAuth2LoginSuccessHandler` with one targeted update (`UserRepository.recordLastLogin`: `set lastLogin = :signedInAt where id = :id`), never a save of the account it loaded, so a password, two-step or `active` change made meanwhile is never written back, whether or not the handler runs in a transaction; a first sign-in creates the account and then records it the same way (`OAuth2SignInWritesTest`). The JWT carries `iat`, which the 15-minute rule reads (`RecentSignIn`).
  - **Legacy `code` on `/login`**: `LoginDto.code` is `@Deprecated(forRemoval = true)`. For one release, `{email, password, code}` still signs in when two-step is on, so a cached old frontend keeps working (log line `Legacy two-factor login user id={}`); TOTP is checked only when an authenticator app is set up, so a keys-only account can pass with a recovery code. **Owner follow-up: remove it in the release after passkeys.** During the deploy gap the old frontend's `/auth/callback` can't read a `pendingToken`, which only affects Google and GitHub sign-ins to accounts with two-step on, so deploy the frontend right after the backend.
- **2FA** (two-step verification):
  - Two flags on `user_account`: `two_step_enabled` (two-step verification is on) and `two_factor_enabled` (an authenticator app is set up, with `two_factor_secret`). Invariant: an authenticator app means two-step is on. 028 turned two-step on for every account that had TOTP.
  - Methods: TOTP (RFC 6238) via `Totp` (hand-rolled, no dep), recovery codes, and passkeys or security keys (see Passkeys). Any account can use them: email and password, Google and GitHub.
  - **Two-step codes** (`TwoStepCodes.normalized`, applied in `DefaultTwoFactorService.verifyLoginCode` and `enable`, so on the second step, the legacy `/login` `code`, turning two-step off, removing the authenticator app and confirming TOTP): all whitespace is stripped (no-break and thin spaces too) and the code upper-cased; an 8-character code without a dash gets one in the middle (`e3hj hdfu` → `E3HJ-HDFU`). A TOTP is then checked as 6 digits (`163 225` → `163225`). A wrong code is still refused and counted.
  - Turn on: confirm an authenticator app (`/auth/2fa/enable`), or with passkeys only (`/users/me/two-step/enable`, needs a passkey). Either issues 10 recovery codes (`RecoveryCodes`, `XXXX-XXXX` from an unambiguous alphabet, bcrypt-hashed in `two_factor_recovery_code`, one use each) only when no unused code is left; otherwise it returns `[]` and the old codes stay. There is no endpoint to issue new codes.
  - Turn off (`/users/me/two-step/disable`, or the old `/auth/2fa/disable` with a code): needs exactly one second factor; deletes the authenticator app and the recovery codes and keeps passkeys, which stay passwordless sign-in methods.
  - Last-method guards: removing the authenticator app needs a passkey left, and removing the last passkey of a keys-only account is refused (exact texts in `DefaultPasskeyService` and `DefaultTwoStepSettingsService`). Every two-step change first takes a `PESSIMISTIC_WRITE` lock on the user row (`AccountLock`, write transactions only), so two requests can't remove both methods at once.
  - A password reset leaves two-step verification as it was, and clears the re-auth wrong-password counter (`reauth:<userId>`).
- **API docs**: admin endpoints hidden from OpenAPI/Swagger via `@Hidden` (whole `AdminController` + admin methods in shared controllers).
- **Hosts** (`CustomHostFilter`, a `FilterRegistrationBean` at `Ordered.HIGHEST_PRECEDENCE + 10`, ahead of Spring Security and `ForwardedHeaderFilter`, error dispatches included; `HostRouting.classify(request.getServerName())`, so `X-Forwarded-Host` is never trusted):
  - **primary**: the host of `app.server-url` plus `app.domains.primary-hosts` (production `hrva.cc,domains.hrva.cc`; the local profile adds `localhost,127.0.0.1`). Everything works as before.
  - **custom**: a hostname the registry holds as `ACTIVE` or `DISABLED`. Only `GET` and `HEAD` of `/` and `/{alias}` (one path segment, not starting with `@`, no `;`, not a built-in reserved alias) are served, by the filter itself, which never calls the rest of the chain. Everything else is a plain 404 (`text/plain`, `Not found`, no-store): `/login`, `/oauth2/**`, `/mcp`, `/api/**`, `/actuator/**`, `/@name`, `/.well-known/**`, any other method. A custom host never serves the API, sign-in, MCP or OAuth under someone else's domain and certificate. A failure while serving is a plain 500.
  - **unknown** (any other host, including a domain not yet `ACTIVE`, an `ERROR` or `DELETED` one, `test.karlo.cc` and a direct request to the container by IP or `localhost` in production): 404, plus one info line per host per hour, `Unknown host refused host=…`, so a missing primary host shows in the logs. Health checks go through `https://hrva.cc/actuator/health`. The primary list must be complete before a deploy (README, production checklist).
  - Redirects from a custom host carry the same no-store headers as the 404s (`Cache-Control: no-cache, no-store, max-age=0, must-revalidate`).

## MCP connector
AI apps (Claude, Claude Code, the MCP Inspector) use hrva.cc over MCP. The app is its own OAuth 2.1 authorization server (Spring Authorization Server through `mcp-authorization-server` 0.1.14), protects `/mcp` as a resource server (`mcp-server-security` 0.1.14) and serves the tools from Spring AI 2.0.2's MCP server. Code: `cc.hrva.urlshortener.mcp` (`authorization/`, `bridge/`, `tools/`, `apps/`). MCP is sign-in only: the no-account server at `/mcp/anon` was removed in v2.11 and now answers 404.

### Security filter chains (in order)
1. **`@Order(1)` authorization server** (`AuthorizationServerConfiguration`): the Spring Authorization Server endpoints, the two 404 discovery paths and `/oauth2/connect/continue`. It keeps an HTTP session from the first `/oauth2/authorize` until the code is issued; the `/mcp` and `/mcp/anon` chains are stateless.
   - `LocalhostWildcardPortValidator`: a localhost redirect URI matches on any port (CLIs such as Claude Code pick a new port per sign-in).
   - DCR validators: redirect URIs (no commas), scope (stored as requested; `openid` and commas rejected), grant types `authorization_code` and `refresh_token` only (`refresh_token` is always granted), response type `code`, size caps (`client_name` ≤ 100, ≤ 5 redirect URIs, column limits). `DcrEmptyScopeFilter` drops `"scope": ""`, which the Inspector sends.
   - `DcrClientSettings`: access token 1 hour, refresh token 30 days and rotated on every refresh, no consent screen (the frontend `/connect` page is the consent).
   - Public-client refresh (`PublicClientRefreshToken*`, token endpoint only), `ResourceIndicatorValidatingProvider` (the `resource` check), `AccessTokenAudienceCustomizer` (a code exchange or refresh without `resource` still gets `aud` = `${app.mcp.issuer}/mcp`; it runs after the library's `resource` customizer).
   - `DisconnectSafeAuthorizationService`: a refresh racing a disconnect gets `invalid_grant` instead of re-creating the authorization.
2. **`@Order(2)` `/mcp` resource server** (`McpResourceServerConfiguration`): `/mcp` and `/.well-known/oauth-protected-resource/**`. RS256 JWTs are checked against the local signing key (no issuer discovery): `iss` = `app.mcp.issuer`, `aud` must contain `${app.mcp.issuer}/mcp`, and `StillAuthorizedValidator` looks the token up in `oauth2_authorization` on every request, so Disconnect is immediate; a database error fails closed as 401 `invalid_token` without infrastructure text. STATELESS, CSRF off.
3. **`@Order(3)` removed `/mcp/anon`** (`McpResourceServerConfiguration.removedAnonymousMcpSecurityFilterChain`, paths `REMOVED_ANONYMOUS_MCP_PATHS`: `/mcp/anon` and `/mcp/anon/**`): an empty 404 for every method and token (removed in v2.11). `denyAll` with an `HttpStatusEntryPoint(NOT_FOUND)`, no authentication filters (a bearer token or app JWT is ignored), CSRF off (otherwise a POST is 403), STATELESS. So an old client gets no `WWW-Authenticate`, which would start an OAuth flow, and never a 401 from the API chain or a 405 from the static resource handler. The body-cap and modern-probe filters no longer list `/mcp/anon`.
4. **`@Order(LOWEST_PRECEDENCE)` API chain** (`SecurityConfiguration`): the existing JWT API and OAuth2 login, plus `/api/v1/connect/**`. `JwtFilter`'s servlet registration is disabled, so it only runs inside this chain.

`/mcp` and `/mcp/anon` never reach `UrlRedirectController`, and `mcp` and `anon` are reserved aliases.

### Login bridge
1. `GET /oauth2/authorize` without a session: `ConnectRedirectEntryPoint` stores the pending request in Redis (`mcp:connect:request:<handle>`, 10 min) and ties the handle to the new session → 302 `${app.frontend-url}/connect?request=<handle>`. Redis down → 503 without infrastructure text.
2. The frontend `/connect` page calls `GET /api/v1/connect/requests/{handle}` with the user's app JWT for the client name, then approve or deny.
3. Approve returns `continueUrl` = `${app.mcp.issuer}/oauth2/connect/continue?otc=<one-time code>` (60 s, single use, redeemed with Redis `GETDEL`). The app JWT never appears in a URL.
4. The frontend navigates the top-level window to `continueUrl`. The code must belong to this browser's session (another browser → 403, a replay → 400). The session id rotates, the session is authenticated as the approving user for 60 s and bound to the approved authorization query → 302 to `/oauth2/authorize?<original query>`.
5. Spring Authorization Server issues the code, and `SessionEndingAuthorizationResponseHandler` ends the session. An authenticated `/oauth2/authorize` with any other query ends the session and starts over (`BridgedAuthorizationRequestFilter`).

### Rate limits
Redis fixed windows (`RedisFixedWindowRateLimiter` in `service/ratelimit/`, key `rate-limit:<name>:<sha256 of the client network>`: the IPv4 address or the IPv6 /64, never a raw IP). The MCP-specific limit (`dcr`) fails closed when Redis is down.
- **`/oauth2/register`**: 20 per hour per network (`dcr`) → 429 with `Retry-After: 3600`; 503 when Redis is down.
- **Signed-in `/mcp` `shorten_url`**: counts toward the account's 60 links per hour (see Security). That limit is not MCP-specific and lets the create through when Redis is down; the refusal is a tool error with its text.
- The client IP comes from `ClientIpResolver`, which trusts `CF-Connecting-IP` (see Security). That is safe only while the origin accepts traffic from Cloudflare alone.
- **Body size**: `McpRequestBodyLimitFilter` (a servlet filter before `DcrEmptyScopeFilter` and Spring Security) caps POST bodies on `/oauth2/register`, `/mcp` and `/api/v1/reports` at 64 KB. A larger `Content-Length` → 413 `{"error":"request_too_large"}`; a body without a length (chunked) fails once it passes 64 KB: 413 on `/oauth2/register`, 400 "Invalid message format" from the MCP transport. `DcrEmptyScopeFilter` also reads at most 64 KB on its own.
- Redis must be 6.2 or newer (`GETDEL`, and `SMISMEMBER` for the blocklists).

### Moderation tools
`mcp/tools/ModerationTools`, beside `LinkTools` on `/mcp`, so an admin can moderate from Claude or ChatGPT. The queue holds text written by scammers that could carry instructions aimed at the assistant, so MCP may only **read and block**:
- Read-only: `moderation_summary` (queue size and visitor reports, blocks in 24 h, possible scammers, failing enabled sources), `review_queue` (20 per page, `reason` filter; visitor report text is left out), `possible_scammers`, `check_url` (the `explain` verdict).
- Destructive: `block_link`, `block_domain`, `block_user`, `delete_link`.
- **Admin only:** every tool first requires `ROLE_ADMIN` on the token's user (`McpUserResolver`) and otherwise refuses with "Moderation tools are for hrva.cc admins only." The tools are still listed to non-admin sessions.
- **Nothing loosens protection:** no Looks fine, Trust domain, Allow rules or unblocking; those stay in the dashboard. Only the dashboard can undo an MCP block.
- **Cap:** `block_domain` and `block_user` refuse, changing nothing, when more than 50 active links would be affected, and point to the dashboard. `block_user` refuses admin accounts.
- **`delete_link` and `block_user` need evidence (R56):** only a blocked link or one with an open `system_flagged` entry, because deleting frees the alias for anyone to register again; otherwise "Only blocked or flagged links can be deleted here. Use the dashboard." `block_user` likewise needs at least one blocked link or open `system_flagged` entry on the account, otherwise "This account has no blocked or flagged links. Use the dashboard to block it."
- **`block_domain` needs evidence:** at least one link on the domain (subdomains included) with an open `system_flagged` entry in the queue or already blocked (R52), and every affected active link with an open `system_flagged` entry (R52b), so a flagged subdomain can't unlock a big parent domain such as `github.io`. A visitor report alone is never evidence (R56), so a report can't talk the assistant into a block. A domain that is itself a public suffix (Guava `isPublicSuffix`, the PSL's private section included: `ddns.net`, `pages.dev`, `github.io`) is refused first with "That's a shared hosting domain. Use the dashboard to block it."; one site on it (`evil.github.io`) can still be blocked. The dashboard has no such limit.
- **Masking:** users appear as a masked email plus id (`r***@gmail.com #27`) and tools take user ids, never emails; destinations appear as host plus path (at most 80 characters, delimited and percent-encoded), never the query or fragment; no IPs or visit details.
- Every action goes through `ModerationService` into the audit log with `via: mcp`.

### Cleanup and revocation
- **`DcrClientCleanupJob`**, daily at 03:30: deletes fully expired `oauth2_authorization` rows, then DCR clients registered more than 30 days ago that have no authorization left (with their consent rows). It never deletes a client with a live authorization.
- Disconnect removes all of the user's authorizations for that client. Deleting or deactivating a user, or changing their email, removes all of their authorizations (`DefaultUserService`).
- Tables (Liquibase 017–021): `oauth2_registered_client`, `oauth2_authorization`, `oauth2_authorization_consent`, with indexes for the token, authorization code, principal and client lookups.

## Scheduled Tasks
Jobs run on a 4-thread scheduler (`spring.task.scheduling.pool.size: 4` in `application.yaml`, threads `scheduling-1`…`4`), so a long job such as the hourly blocklist refresh can't stall the per-minute ones.
- **Blocklist refresh**: Every hour, `refreshDue` downloads each enabled source whose own interval (`refreshIntervalHours`, 1–168, default 6; 5 minutes' tolerance) has passed or whose Redis set is missing. `reloadMissing` (`@Async`) downloads every enabled source whose set is missing, at startup (`ApplicationReadyEvent`) and every 5 minutes (`reloadMissingBlocklists`, 30 s past the minute): one `EXISTS` per source, and while Redis is down one warn line and nothing else until the next run. So a Redis restart or `FLUSHALL` heals itself within minutes, without an app restart.
- **Click-check lists**: Every 5 minutes, at startup and after any source or rule change (`BlocklistConfigurationChangedEvent`), `DefaultClickCheckService.reload` re-reads the enabled `BLOCK` source ids and the Allow-rule domains into memory.
- **URL expiry**: Daily at 8 AM, emails the owners who turned on expiry reminders (`EXPIRY_REMINDER_EMAIL`, active account) about links expiring within 24 hours (`app.url-expiration-notification-hours`). Since v2.14 it is opt-in: existing users get none until they turn it on. The links and the consenting owner ids come from one read-only transaction, and each send checks the consent again.
- **Daily click summary** (`DefaultClickSummaryService.sendDaily`): 01:15 in `app.analytics.zone`, yesterday's clicks to channels with `DAILY_SUMMARY` (see Notifications and consent).
- **Destination check** (`DefaultDestinationCheckService.runNightly`): 02:00 in `app.analytics.zone`, then the dead-link notices (see Notifications and consent).
- **Notification deliveries**: every 60 s (`fixedDelay`), `drainNotificationDeliveries` hands off to `@Async drainInBackground()`, which sends up to 20 due deliveries.
- **Notification cleanup**: daily at 03:55, `deleteOldNotificationRecords` deletes deliveries created over 30 days ago and claims over 60.
- **Weekly summary** (`DefaultClickSummaryService.sendWeekly`): Mondays at 09:00 in `app.analytics.zone`, last week's summary by email and to channels.
- The destination check (with the dead-link notices after it), the drain and both summaries only hand off from the scheduler thread to `notificationTaskExecutor` (`@Async("notificationTaskExecutor")`, see Executors), so click recording and the `@Async` emails never wait behind them, and an `AtomicBoolean` in each service skips a run that would overlap the last one (`longJobsRunAsync`, `anOverlappingRunIsSkipped`).
- **Reset tokens**: Every minute, deactivates and deletes expired password reset tokens.
- **URL deactivation**: Every minute, deactivates expired URLs with a targeted update by id (`deactivateIfActive`), never by saving loaded copies, so a block landing meanwhile stays.
- **API key deactivation**: Every hour, deactivates expired API keys.
- **User deactivation**: Daily at 10 AM, deactivates unused accounts after configured inactivity period.
- **MCP cleanup**: Daily at 03:30, deletes expired OAuth authorizations and DCR clients unused for 30 days (`DcrClientCleanupJob`).
- **Log retention**: Daily at 03:50, `deleteOldLogs` deletes `email_log` rows whose `created_at` is older than `app.retention.email-log-days` (default 90) and `audit_log` rows whose `performed_at` is older than `app.retention.audit-log-months` (default 12), one bulk `DELETE … where … < :cutoff` per table (never load-then-delete; no foreign key references either table), and logs `Scheduled cleanup: old logs emailLogsDeleted=N auditLogsDeleted=M`. Tests: `LogRetentionRepositoryTest` (old rows go, rows at or after the cutoff stay, an empty table deletes nothing) and `DefaultScheduledServiceTest` (the cutoffs from the configured periods, the cron).
- **Bio handle holds**: Daily at 03:45, `releaseExpiredBioHandles` deletes the holds whose 30 days have passed with one bulk `delete from BioHandleHold h where h.heldUntil < :now` (never load-then-delete, which could remove a hold renewed in between) and logs `Scheduled cleanup: expired bio handles released=N`.
- **Nightly scan** (`DefaultSafeBrowsingRecheckService`): Daily at 04:30, walks every active link by id (so deactivations mid-run don't skip rows) through the link check and Safe Browsing. List hits, admin Block rules and Safe Browsing block the link (deactivated, evicted from the cache, owner emailed); a `SCAM_SIGNALS` verdict and every flag go to the review queue instead, unless the same reasons were already marked fine. It then follows the redirect chains of up to 500 active links whose `chainCheckedAt` is null or over 7 days old, oldest first. Once Safe Browsing fails, the run stops calling it, finishes with the link checks only and skips the redirect checks.
- **Interrupted emails**: Every 5 minutes, `email_log` rows still `SENDING` after 10 minutes become `FAILED` ("interrupted") so they can be resent.
- **Decisions email** (`DefaultLinkDigestService`): Daily at 9 AM, emails `app.contact-email` "N decisions waiting on hrva.cc", only when something needs a decision: an open review entry, a link blocked automatically in the last 24 h (any block reason but `ADMIN` and `USER_BLOCKED`, the set `BlockReason.MANUAL` that the weekly digest shares), or an enabled source whose last download failed. It lists the open count and the visitor reports among them, the newest 10 entries (each linking to the queue page; a visitor report shows only its category, never the visitor's text, through `ReviewReasons.withoutVisitorText`, which `review_queue` uses too), up to 10 possible scammers, the automatic blocks and the failing sources, plus an information-only section of links from accounts younger than 7 days that never triggers sending alone. Open bio page reviews count too: they alone send the email, the subject's N adds them, and one line says how many bio pages wait, with a `Review bio pages` link to `/admin/review#bio-pages`. No link in it acts by itself (mail scanners prefetch links).
- **Discord alerts** (`DefaultDiscordAlertService`): every 30 s, posts what happened since the last flush to the Discord webhook in `app.discord-webhook-url` (`DISCORD_WEBHOOK_URL`) as one message, and once more when the app shuts down (see Discord alerts).
- **Custom domain lifecycle** (`runDomainLifecycle`): every 60 s (`fixedDelay`, first run 30 s after startup), hands off to `@Async` `CustomDomainLifecycle.runInBackground()` on `notificationTaskExecutor` (an overlapping run is skipped): due setups, checks and queued Cloudflare deletes (see Custom domains, ruling 25). Nothing depends on an in-memory schedule, so a restart catches up on the next run. An approval also starts its setup right after the commit.
- **Custom domain routes** (`reloadCustomDomainRoutes`): every 60 s, `CustomDomainRegistry.reload()` re-reads the `ACTIVE` and `DISABLED` domains and their owners' state (also once every bean exists, before the server takes requests, and after each domain write commits).
- **Custom domain reconcile** (`reconcileCustomDomains`): 03:40 in `app.analytics.zone`, `CustomDomainReconciler.reconcileInBackground()`: the Cloudflare comparison, then the link check over every `ACTIVE` hostname (see Custom domains, rulings 17 and 24). At startup (`ApplicationReadyEvent`, `@Async`) it runs the comparison once when the newest recorded run is older than 26 hours or there is none (`Custom domain reconcile startup catch-up …`), without the hostname check.
- **Cloudflare token check**: once at startup (`ApplicationReadyEvent`, `@Async`, fail-soft), then on demand, before every approval or setup retry and at the start of each reconcile; there is no timer.
- **Weekly digest** (`DefaultWeeklyDigestService`): Mondays at 08:00 in `app.analytics.zone` (`@Scheduled(cron = "0 0 8 * * MON", zone = "${app.analytics.zone}")`, log line `Scheduled: weekly digest`), last week's summary to Discord and to `app.contact-email`, at most once per week (see Weekly digest).

## New Models (recently added)

### AuditLog (`audit_log` table, migrations `008-audit-log.xml`, `025-audit-log-typed-action.xml`)
- Tracks admin actions: performedBy, action, failed, targetType, targetIdentifier, details, performedAt
- `action` is an `AuditAction` (`model/enums`), stored by name (`@Enumerated(EnumType.STRING)`): one constant per audited controller method (`REVOKE_URL`, `UPDATE_USER`, `CREATE_SOURCE`, …), the `ModerationService` actions (`RESOLVE_REVIEW`, `BLOCK_LINK`, `BLOCK_DOMAIN`, `ALLOW_DOMAIN`, `REMOVE_DOMAIN_RULE`, `BLOCK_USER`, `REACTIVATE_USER`, `DELETE_LINK`), the reserved-alias actions (`RESERVE_ALIAS`, `UNRESERVE_ALIAS`, target type `ReservedAlias`), the bio page actions (`HIDE_BIO_PAGE`, `UNHIDE_BIO_PAGE`, `RENAME_BIO_HANDLE`, `REVOKE_BIO_HANDLE` with target type `BioPage`, `RESOLVE_BIO_REVIEW` with `BioPageReview`; the target is the page id) and `UNKNOWN`, which only migrated rows carry. A bio handle revoke writes two rows on purpose: `REVOKE_BIO_HANDLE` from the aspect and `RESERVE_ALIAS` from `ReservedAliasService` (none when the handle was already reserved).
- Auto-logged via `AdminAuditAspect` around the controller methods annotated `@Audited(AuditAction.…)`; the annotation names the action, so a method can't be audited without one. `AuditedMethodsTest` pins the audited methods and their actions, so adding or dropping one fails until the test is updated. `targetType` is the controller name without `Controller` and a leading `Admin` (`AdminEmailLogController` → `EmailLog`), unless `@Audited(targetType = …)` names it: the domain limit actions are recorded against the `User` they belong to. The aspect's target is the first argument when it's a plain value (an id), otherwise the `id` of the response body.
- `ModerationService` and `ReservedAliasService` log their own actions instead, because the aspect can't see what they act on (a domain, or an alias that's gone once it's removed). They write the row after their transaction, a failure's row too, so it survives the rollback. Reserved aliases: `targetIdentifier` is the alias as matching stores it (trimmed, lower-cased), for `RESERVE_ALIAS`, `UNRESERVE_ALIAS` and a failed reservation (409 `This alias is already reserved.`, its message as details); `details` is `reason: <reason>`. A removal of an unknown id (404) keeps the id as its target. Rows written before v2.9 keep an id as their target, the created entry's (`RESERVE_ALIAS`) or the removed one's (`UNRESERVE_ALIAS`), and a failed attempt's target is empty; there's no backfill.
- A request refused by bean validation (`@Valid`, 400 `{"field": "message"}`) never reaches the action and is never audited, on any endpoint.
- `details` lists only the submitted, non-null fields of the request body, alphabetically (`longUrl: …, visitLimit: 10`); a password is written as `changed`/`removed`, never its value. A failed action keeps its action with `failed = true` (`AuditLogService.logFailure`) and the exception message as details. Migration `023-audit-log-redact-url-passwords.xml` redacted the link passwords older rows held in plain text.
- Migration 025 added `failed` and rewrote the old free-text actions: the aspect's camelCase method names (every one it ever audited) became their constants, a `…_FAILED` suffix became the base action with `failed = true`, and anything else became `UNKNOWN`, its old value copied into `details` when those were empty. `AuditActionMigrationTest` runs it on legacy rows.
- Endpoint: `GET /api/v1/admin/audit-log` (`?action=`)
- Kept 12 months (`app.retention.audit-log-months`), then deleted by the nightly log retention job

### EmailLog (`email_log` table, migration `009-email-log.xml`)
- Records email sending: sender, recipient (comma-separated), subject, status (SENDING/SENT/FAILED/RESENT), errorMessage, sentAt, createdAt, body
- Populated automatically by `tryToSendEmail` in `DefaultSendingEmailService`, which retries 3 times and records any failure (checked or runtime) as FAILED with its message
- An email with a plain-text part (`Email.plainText`, only the weekly digest so far) is sent as `multipart/alternative`; the plain text is never stored, so a resend from the log sends the HTML only
- Rows are kept 90 days (`app.retention.email-log-days`), then deleted by the nightly log retention job
- `body` (migration `022-email-log-resend.xml`) holds the rendered HTML only until the email is sent, and at most 7 days for failed ones (daily 03:15 cleanup); it is `@JsonIgnore`d and exposed as the `resendable` flag (FAILED with a body)
- `status` is a string column; `model/enums/EmailStatus` names its four values (the `EmailLog.STATUS_…` constants are its names) and binds the log's `?status=` filter (`findAllByStatusOrderByCreatedAtDesc`)
- **Consented emails** (migration 031 adds `consent_type` and `user_id`, no FK): the dead-link email, the weekly summary and the expiry reminder go through `tryToSendConsentedEmail(email, userId, type)`, which checks the consent again right before sending (`EmailConsentReader`: an active consent row AND an active account), stores `consent_type` and `user_id`, and adds `List-Unsubscribe: <{serverUrl}/api/v1/notifications/unsubscribe?token=...>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. A resend re-checks it by `user_id` and refuses with `This person has turned this email off since, so it can't be resent.`; a consented row without `user_id` is refused the same way. The admin email log JSON carries `consentType` and `userId`.
- The welcome email is gone (v2.14): verifying an address sends nothing; the frontend's verification success screen carries its line.
- Endpoints: `GET /api/v1/admin/email-log` (`?status=`, see Key Endpoints); `POST /api/v1/admin/email-log/{id}/resend` (admin, synchronous) sends a stored failed email again as a new row and marks the old one RESENT

### Abuse handling
- `SuspiciousUrlService` flags destinations by host: other shorteners (and our own host), free dynamic-DNS hosts, raw IPs (an IPv6 host, four dotted numbers, or any host a browser reads as an IPv4 address, such as `127.1` or `0x7f.0.0.1`, see Host normalisation), lookalikes of known brands on someone else's domain (`njuskaio.cam`, `jofogas.cards`), login/verification lures, high-risk TLDs, and international names that mix alphabets or aren't Latin (see International names). Flags only; it never deactivates anything.
- **Host normalisation** (`DomainNames.hostNameOf` → `HostName(ascii, unicode)`; `DomainNames.hostOf` is the ASCII form). The link checks read a user-supplied host only through `DomainNames`, never `URI.getHost()`, which returns null for a Unicode or underscore host: that null once made `SuspiciousUrlService` skip every rule, so `https://pаypal.com/login` (Cyrillic `а`) was saved as active and never reviewed, and `https://ｂｉｔ．ｌｙ/x` passed the shortener refusal.
  - ASCII form: `DomainNames.toAscii`, which lower-cases, runs `IDN.toASCII` with `IDN.ALLOW_UNASSIGNED` and lower-cases again. `ALLOW_UNASSIGNED` keeps letters newer than Unicode 3.2 (Java's IDN is IDNA2003) convertible, so `аррӏе.com` is `xn--80ak6aa92e.com` instead of unreadable; never add `USE_STD3_ASCII_RULES`, which refuses underscore hosts. Lower-casing first maps `Ӏ` to `ӏ` like a browser, so `АРРӀЕ.com` is the same `xn--80ak6aa92e.com`. Full-width letters and dots become ASCII (`ｂｉｔ．ｌｙ` is `bit.ly`), then the trailing dot is stripped; an IPv6 host loses its brackets. A host a browser reads as an IPv4 address (WHATWG: the last label is a number; hex `0x7f.0.0.1`, octal `0177.0.0.1`, short `127.1`, a single number `2130706433`) becomes that address in dotted decimal (`127.0.0.1`), so the link checks flag it `IP address instead of a domain` and the redirect check's public-address guard refuses it as loopback; a numeric-looking host that isn't a valid address (`1.2.3.256`, `999.1.1.1`) stays as written.
  - Unicode form: `DomainNames.toUnicode` (`IDN.toUnicode` of the ASCII form, also with `ALLOW_UNASSIGNED`, lower-cased). An `xn--` label that doesn't decode stays as it is.
  - Domain matching uses the ASCII form, so a Unicode spelling matches the same entries as its punycode: domain rules, blocklist sources and link keys, the click check, Spamhaus DBL, RDAP, the shortener and dynamic-DNS lists, `RedirectLocations` for redirect hops, and MCP `block_domain`'s evidence search (which also searches the Unicode form). Script and look-alike checks use the Unicode form. Call `DomainNames.toAscii` / `toUnicode`, never `IDN` directly.
  - The redirect check normalises every URL before its public-address guard and its request, the destination included (see Redirect chains), so a Unicode destination's redirects are followed and checked like any other, and a Unicode or full-width spelling of a private or loopback address (`ｌｏｃａｌｈｏｓｔ`, `１２７．０．０．１`) is refused as its ASCII form. `PublicAddresses.isPublicTarget` itself still reads `URI.getHost()` and refuses any non-ASCII host, which is why callers pass it the normalised URL; the link preview, which connects through Jsoup's own IDN conversion, keeps refusing Unicode hosts rather than risk the guard and the connection resolving different names.
  - `checkIfLongUrlIsValid` reads the host with Spring's WHATWG parser for validity only: it accepts Unicode hosts but refuses a letter newer than Unicode 3.2 with "That doesn't look like a valid web address", so `https://аррӏе.com` can't be created while its punycode can (and is flagged). `DomainNames.HOST_NAME` caps each label at 63 characters (DNS), so a host such as `<64 letters>.bit.ly`, which `IDN` can't convert and the shortener refusal would never see, is refused there too, and `DefaultUrlValidator.isHostName` also refuses a host longer than 253 characters (the DNS maximum, measured on the parser's ASCII form, so an IDN counts as its punycode, without a trailing dot) with the same message, on create and on the admin destination edit; that also bounds every host an alert line can show. The blocklist parser, the referrer classifier and the domain age and reputation lookups skip such names.
  - Known limitation: `java.net.IDN` is IDNA2003 while browsers use UTS #46, so `faß.de` becomes `fass.de` here but `xn--fa-hia.de` in a browser (likewise `ς`, ZWJ/ZWNJ); an entry listing `xn--fa-hia.de` matches only that spelling.
- **International names** (`DefaultSuspiciousUrlService`, per label of the Unicode form, so both spellings of a host get the same reasons):
  - A label that mixes alphabets → `mixes Latin and Cyrillic letters` (the scripts named, by `Character.UnicodeScript`, ignoring `COMMON` and `INHERITED`). Latin with Han, Hiragana, Katakana, Bopomofo or Hangul in the combinations of UTS #39's highly restrictive level doesn't count as a mix.
  - A label with an unassigned character (`Character.UnicodeScript.UNKNOWN`) beside letters reads `mixes Latin letters with unusual characters` (the alphabets named, then "with unusual characters").
  - Any other label with a non-ASCII character that isn't a Latin letter (a whole label in one non-Latin alphabet such as `пример.рф`, a symbol or emoji such as `i♥ny.com`, a usual Japanese mix such as `日本の.jp`), or an `xn--` label that doesn't decode → `punycode domain`, as before. The Catalan middle dot `·` (U+00B7) between two `l`s is the exception (UTS #46's CONTEXTO rule), so `col·legi.cat` gets no reason; a middle dot anywhere else is still flagged.
  - A Latin-only label with diacritics (`čokolada.hr`, `žabica.hr`, `müller.de`) gets no reason for being international. Before v2.9 every `xn--` spelling was flagged `punycode domain` and every Unicode spelling skipped all checks.
  - The brand and host-lure checks run on each label's Latin look-alike, the skeleton: the label is decomposed (`Normalizer` NFD) and its marks (`\p{M}`) dropped, so diacritics fold away (`á` → `a`, and a combining accent on a Cyrillic letter); then `LATIN_LOOKALIKES` maps the Cyrillic and Greek letters that look Latin (`а е о р с у х і ј ѕ ӏ ԁ һ ԛ ԝ ѵ`, `ο ρ ν α ι κ υ χ γ ϲ ϳ`), `ı ɑ ɡ` and the Latin letters with a stroke (`ł đ ø ð ħ ŧ`) to their Latin twins, with no dependency. So all-Cyrillic `аррӏе.com` → `punycode domain` and `imitates apple`, `pаypal.com` → `mixes Latin and Cyrillic letters` and `imitates paypal`, `ñetflix.com` → `imitates netflix`, `ápple.com`, `dhł.de` and `pâypál.com` → `imitates apple`, `dhl`, `paypal`, and `vérify.evil.com` → `login or verification lure`, in either spelling. The skeleton is only for these checks: the alphabet rule above reads the label as written, so `čokolada.hr`, `müller.de`, `hôtel-paris.fr` and `www.đakovo.hr` still get no reason.
  - `mixes …` and `punycode domain` are Flags: they send the link to review and are never scam signals, so on their own they don't block a young domain.
- `GET /urls/all` (admin) returns `suspiciousReasons` per link (omitted when empty), and `blockReason`, `reviewOpen`, `ownerPossibleScammer` and `finalUrl` (omitted when null); searching matches the short link, destination and owner email; `?anonymous=true` keeps links without an owner; sort by owner with `sort=owner.email,asc`.
- **Search terms** (`repository/specification/`): destinations are stored as typed, so both URL searches, the owner's `GET /urls?search=` (`UrlSpecification.search`: destination and short link) and the admin's `GET /urls/all?search=` (`searchIncludingOwner`: also the owner email), also match the other spelling of a host term (`spellingsOf`). The term is lower-cased and read with `DomainNames.hostNameOf`; when its ASCII and Unicode forms differ and the ASCII form is a dotted host name, the term is also searched with the host swapped (`čokolada.hr` ↔ `xn--okolada-i6a.hr`, in a full URL or an email too), or with both bare full forms when the host is typed half in each spelling (`čokolada.xn--p1ai`). A plain ASCII host, a word without a dot and a term the parser can't read match as typed. `%`, `_` and `\` are plain text in the URL, user and review-reason searches: `LikePatterns.containing` escapes them and every `like` declares `ESCAPE '\'`.
- New links and admin destination changes pointing at a generic shortener (bit.ly, tinyurl, …) or at hrva.cc are rejected (`checkIfLongUrlIsNotAShortener`). Platform share links (t.co, lnkd.in, goo.gl) are only flagged, and Google's `*.app.goo.gl` share links are neither.
- A blocked link has a `blockReason` (`SAFE_BROWSING`, which also sets `threatType`, `BLOCKLIST`, `DOMAIN_RULE`, `ADMIN`, `USER_BLOCKED`, `SCAM_SIGNALS`), a `blockDetail` (the list, rule or signal, cut to 255 characters with `StringUtils.abbreviate` like a rule's reason, so a long admin or MCP reason can't fail the block) and `blockedAt`; its status is BLOCKED. Owners can't reactivate it; admins can, which re-runs the checks unless the domain is allow-listed. Every reactivation re-checks Safe Browsing and that no other active link holds the alias. `Url` has no `@Version`, so `updateUrl` and `activateUrl` run their checks outside a transaction (`NOT_SUPPORTED`), re-read the row in the write transaction and refuse with `This link was blocked while you were editing it. Reload and try again.` when it gained a block meanwhile; otherwise the edit is applied to the re-read row, so a stale copy never writes back `active` or the block fields. With open-in-view off (see Database) every call in such a method has its own `EntityManager`, so the re-read always comes from the database and the copy loaded at the start is already detached. The link and the signed-in user come from different transactions, so the owner check compares ids. Never modify the copy loaded at the start; edit a copy of it (`UrlUpdateDtoToUrlConverter` returns one, with its own tag set) and apply that to the re-read row. Before v2.8.3, with open-in-view on, an owner's refused destination change was saved because the failure's audit row flushed the modified copy. A blocked link's owner is emailed (`url_blocked.html`), except when the whole account is blocked. A domain block (a Block rule, MCP `block_domain`, Block domain from the review queue, single or bulk) and a bulk Block link from the review queue email each owner once, after all the links are blocked: an owner with one link gets `url_blocked.html`, an owner with several gets `urls_blocked.html` ("Your links were blocked as unsafe"), which lists the first 20 short links and then "and N more". Like the single email, it never names the rule, the list or the destination, and a failed email to one owner doesn't stop the others.
- Bio page buttons are their owner's own short links, so every click goes through the redirect and every check here, and a button whose link is blocked, deactivated, expired, at its limit or in an open `system_flagged` review disappears from the page (see Bio pages).
- A custom alias stays taken while any row (active or not) holds it, so an expired link's alias can't be claimed by someone else.
- A reserved alias (the built-in words and the admin's `reserved_alias` entries, see ReservedAlias) can't be taken on any create path, in any case, and generated aliases skip it. Reserving an alias a link already holds changes nothing for that link; the admin list shows it under `inUse`.
- **Link checks** (`LinkCheckService.check`, called by `validateUrl` and `updateUrl` on every create path, MCP included, before the write transaction; `explain` runs every lookup and lists every match for the url-check and `check_url`). The verdict is for the destination host, matched on the host's ASCII form (see Host normalisation) and each parent domain. In order:
  1. **Allowed**: an admin Allow rule skips the domain lists, domain age, Spamhaus and the heuristics. The most specific matching rule wins, so a Block on `evil.example.com` beats an Allow on `example.com`. Exception (R35): an exact-link entry on an enabled `LINKS` Block source still blocks, because it names that one URL.
  2. **Block**: an admin Block rule (`DOMAIN_RULE`), an enabled `BLOCK` source (`BLOCKLIST`, the source name), Spamhaus DBL phish, malware or botnet (`BLOCKLIST`, `Spamhaus DBL: <type>`), or a domain younger than 30 days with a lookalike or login-lure heuristic (`SCAM_SIGNALS`).
  3. **Flag**: a lookalike plus a lure on an older domain, an enabled `FLAG` source, Spamhaus spam or an abused legitimate domain, a domain younger than 30 days, or any other `SuspiciousUrlService` reason.
  4. Otherwise clean. An unknown domain age never counts. A blank destination is clean; a non-blank one whose host can't be read is a Flag (`destination host could not be read`), which only the nightly scan and redirect hops can meet, because creating such a link fails `checkIfLongUrlIsValid` first. Safe Browsing and the shortener refusals run whatever the verdict.
- On create or a destination change, a Block → 400 "This destination is on a blocklist and can't be shortened. If you think that's a mistake, contact us." (the list is never named); a Flag saves the link and opens a review entry with its reasons.
- **Domain age** (`DefaultDomainAgeService`): RDAP through the IANA bootstrap registry for the registry domain, 3 s timeout; failures and registries without dates (`.de`, `.hr`) are unknown. **Spamhaus DBL** (`DefaultDomainReputationService`): only with `SPAMHAUS_DQS_KEY`, `<name>.<key>.dbl.dq.spamhaus.net` for the host and its registrable domain, 2 s timeout; on create and nightly, never on a click.
- **Blocklist sources** (`blocklist_source`, managed in the dashboard; nothing depends on HaGeZi). Kind `DOMAINS`: plain, hosts (`0.0.0.0 d`), adblock (`||d^`) and wildcard (`*.d`) lines; `@@` exceptions and full-URL lines are skipped. Kind `LINKS`: one `http(s)://` link per line, or a CSV's `url` column; keys drop the scheme, default port and fragment (`LinkKeys`), percent-encode raw spaces, non-ASCII and `"<>{}|^` in the path and query with `RedirectLocations.percentEncoded` (so a raw and an encoded spelling are one key, on the feed side and the link side alike), and match with or without the query. Downloads: https and public addresses only (re-checked on every hop), the main URL then up to 3 fallbacks in order, ETag/Last-Modified sent only to `lastSuccessUrl`, caps of 100 MB and 5 M entries. Zero entries, or fewer than 90 % of the count a header declares, fail. **Shrink guard**: when the list declares no count, a scheduled refresh (`refreshDue`, `reloadMissing`) that reads fewer than half of a stored `domainCount` of 1,000 or more, while that set is still in Redis, fails with "The new download has N entries, less than half of the M loaded before. Kept the old list." (the next URL is tried); Refresh now skips the guard, so a list that really shrank can be accepted. A failure keeps the old set and records `lastError` (every failed attempt, even when a fallback then succeeded). After the download, `BlocklistRefresher` re-reads the source from the database; a source disabled, deleted or switched to another kind meanwhile keeps that change, its Redis set is not re-created and the download is dropped, and the result is written with a targeted update of the refresh columns only (`recordLoadedList`: `last_fetched_at`, `last_error`, `last_success_at`, `last_success_url`, `domain_count`, `list_version`, `etag`, `last_modified`; `recordRefresh`: `last_fetched_at` and `last_error` when nothing was stored), guarded by `where id = ? and enabled = true and kind = ?`, never a merge of the row. So another admin's change made during the download or the Redis write stays (a rename or a new interval is kept next to the new list); when the guard matches no row, the source was disabled, deleted or switched kind while its list was stored, and the set just written is removed (`blocklistStore.remove`; a Redis failure there is logged) and no alert is sent. The row is re-read after the update, and both the health alert and the response use it, so a source renamed meanwhile is alerted under its new name. `BlocklistSource` is `@DynamicUpdate` and an admin edit loads and saves the row in one transaction, so the edit writes only the columns it changed and a refresh recorded meanwhile keeps its columns. A URL change made during the Redis write is not part of the guard: the list from the old URL is recorded and the next refresh downloads the new URL in full. A source URL can carry an access key (URLhaus Auth-Key), so download log lines name the source and the attempt (`main`, `fallback 1`), never the URL, and the audit details of a source create or update leave out `url` and `fallbackUrls`. **Memory guard**: a load that would take Redis past 80 % of `maxmemory`, or past `app.blocklists.max-redis-mb` across all sets when there is no `maxmemory` (estimated at 100 bytes per domain, 200 per link), is refused.
- **Seeds** (024): HaGeZi TIF medium and Fake (`BLOCK`), badware hosters, DynDNS and URL shorteners (`FLAG`), every 6 h from `hagezi-mirror.dnsbunker.org` with the same GitHub path as fallback; URLhaus (1 h), OpenPhish (12 h) and PhishTank (6 h) as `LINKS` `BLOCK`, URLhaus switched off (since October 2026 its downloads answer 410 without a free abuse.ch Auth-Key in the path, `https://urlhaus-api.abuse.ch/v2/files/exports/<key>/…`; put that URL in the source, then enable it); Phishing.Database active domains (`FLAG`, 24 h). Block rules for `njuskaio.cam`, `jofogas.cards`, `info-auth.com` and `app-onlinebanking.de`.
- **Click check** (`ClickCheckService.mayRedirect`): before a visitor is sent anywhere (the redirect from the cache or the database, `/unlock`), the destination's domains and link keys are looked up in the enabled `BLOCK` sources' sets in one pipelined `SMISMEMBER` round trip. A match blocks the link (`BLOCKLIST`, the source name, via `click`) and the visitor goes to `/unavailable?reason=blocked`; `GET /urls/{short}`, `/peek`, `/preview` and `/qr` answer a match like a missing link. An Allow rule skips the domain sets. A Redis failure lets the visitor through; a failure while blocking still refuses. `FLAG` sources, RDAP, Spamhaus, heuristics and Safe Browsing are never used on a click.
- **Domain rules** (`domain_rule`, a rule covers the domain and its subdomains): a Block deactivates and blocks every active matching link (evicted from the cache, each owner emailed once, audited), sparing links a more specific Allow trusts. Block domains on All URLs previews the ticked links' registrable domains and blocks the ones the admin keeps ticked in one call (`/domain-rules/bulk`), each like a single Block, with one email per owner across all of them. An Allow resolves the domain's open queue entries as `DOMAIN_TRUSTED` and restores its `BLOCKLIST`, `SCAM_SIGNALS` and `DOMAIN_RULE` blocks after a fresh check, never `SAFE_BROWSING` or `ADMIN` ones. Block user deactivates the account and blocks its links as `USER_BLOCKED` (one account email, no per-link emails, never an admin); unblocking restores those links.
- **Review queue** (`link_review`): one open entry per link with newline-joined reasons (resolved one by one or up to 100 at a time, see Key Endpoints); a new reason extends it. After Looks fine (`OK`) the link re-enters only with a new reason. A destination change resolves the open entry as `DESTINATION_CHANGED` and re-flags if needed. Visitor reports add `reported by a visitor: <category>[: details]` (at most 20 report lines); `<category>` is the lower-cased name (`phishing`, `malware`, `spam`, `impersonation`, `other`), the label Discord and the decisions email show too. `system_flagged` marks an entry the checks flagged: `flag` sets it, `report` never does and leaves it as it was, so an entry only visitors reported has it false. `ReviewQueueService.flag` and `resolveOpen` must never run inside a read-only transaction, which would silently drop the write.
- **Possible scammer** (`ScammerSignalService`, computed, never acted on automatically): an account younger than 7 days with 2 or more flagged or blocked links (flagged: a `system_flagged` entry not resolved `OK` or `DOMAIN_TRUSTED`; visitor reports never count), 3 or more blocked links in total, or 10 or more links within 24 h of signup (only for accounts younger than 30 days). Deactivated and admin accounts are left out. The id set is a 60 s snapshot, refreshed on block and unblock.
- **Redis keys** (all through `StringRedisTemplate`; every caller is fail-soft, see Performance):
  - `blocklist:source:<id>`: one set per source (domains, or link keys without the scheme), loaded into `blocklist:source:<id>:loading` (expires after 2 minutes) and swapped in by a Lua script that checks `SCARD`, then `RENAME`s and `PERSIST`s. Memory is read with `MEMORY USAGE` inside Lua.
  - `rdap:<registry domain>` (30 days with a date, 1 day without one, 1 hour after a failure) and `rdap:bootstrap` (1 day)
  - `dbl:<name>`: Spamhaus answers, 1 hour
  - `rate-limit:create:anon:<sha256 of the network>`, `rate-limit:create:user:<id>`, `rate-limit:report:<sha256 of the network>`, `rate-limit:public-stats:<sha256 of the network>` (the public numbers, 1 hour), beside the MCP and `/unlock` ones
  - `digest:weekly:<yyyy-MM-dd of the week's Monday>`: the weekly digest's once-a-week claim, 8 days (see Weekly digest)
  - `burst:links:<registrable domain>`: a sorted set of `<urlId>|<creator>` members scored by creation time, expiring after `app.burst.window` (the TTL renews on every write and older members are pruned only on the next write, so a member can live up to twice the window); `burst:alerted:<registrable domain>`: `1` for 24 hours after an alert (see Burst alert)
  - `public:stats`: the public numbers as JSON, 1 hour (see Public numbers)
  - the `digest:`, `burst:` and `public:` keys count under `other` on the System tab
  - `analytics:salt:<yyyy-MM-dd>` and `analytics:visitors:<urlId>:<yyyy-MM-dd>`: the day's salt and each link's visitor set, both expiring at the next midnight in `app.analytics.zone` plus 4 hours (see Click analytics)
  - bio pages (see Bio pages): `analytics:bio-visitors:<pageId>:<yyyy-MM-dd>` (each page's visitor set, with the links' salt and expiry), `rate-limit:bio-save:user:<id>` (60 per hour), `rate-limit:bio-handle:user:<id>` (5 per 24 hours, spent only by a create or handle change that succeeds), `rate-limit:bio-handle-check:user:<id>` (120 per 10 minutes) and `rate-limit:bio-view:<sha256 of the network>` (60 views a minute). Every bio limit fails open: Redis down allows the request with one warn line and no IP
  - notifications: `rate-limit:notify-settings:user:<id>` (60 per hour, consent changes and channel create, edit and delete; fails open with one warn line), `rate-limit:notify-test:user:<id>` (10 per 10 minutes, Send test and New signing secret; fails closed, 503) and `RateLimiter.clientKey("unsubscribe", ip)` (30 per 10 minutes per network; fails open)
  - sign-in state, which fails closed instead (see Passkeys): `auth:pending-login:<token>` (5 minutes), `rate-limit:pending-login:<token>` (its 5 attempts, 5 minutes), `passkey:ceremony:<ceremonyId>` (5 minutes, read with `GETDEL`), `rate-limit:passkey-options:<sha256 of the network>` and `rate-limit:passkey-second-step-options:<sha256 of the network>` (30 per 10 minutes each)
- **Redirect chains** (`RedirectChainService`): after a create or a destination change (`@Async("redirectCheckExecutor")`, 2 threads and a 200-check queue, once the save has committed; a full queue is logged and left to the nightly), and in the nightly scan for up to 500 active links whose `chainCheckedAt` is null or over 7 days old, the destination's HTTP redirects are followed: at most 5 hops in 5 s, GET with headers only, http or https, each hop through the public-address guard (a refused destination is a fetch error; a refused later hop ends the chain unrequested). The destination and every `Location` are read like a browser does before the guard sees them and before they're requested (`RedirectLocations.normalized`: UTF-8 bytes, `\` as `/`, space, non-ASCII and `"<>{}|^` percent-encoded, host through `DomainNames.toAscii`). `RedirectFollower` returns each hop as a `RedirectHop(original, normalized)`: `normalized` is what was guarded and requested and what every check uses; `original` is what's stored, the destination as typed for the first hop, an absolute `Location` as received (after UTF-8 decoding), and a relative `Location` resolved against the hop that sent it (in its normalised form, because a relative reference has no host of its own). A hop whose normalised form equals the destination's is not judged again. Every hop after the destination goes through `LinkCheckService.check` and Safe Browsing and the worst hop wins: a block blocks the link (`via redirect to <host>`), a flag or scam signals queue it (`redirects to <host>: <reason>`), unless the link was repointed meanwhile. `finalUrl` (the last hop's `original`: the last `Location` as received, or the destination as typed when nothing redirected) and `chainCheckedAt` are stamped with targeted updates; a fetch error stamps only `chainCheckedAt`, and a Safe Browsing outage stamps nothing (the nightly skips or stops its redirect checks) so a later run retries. The fetcher is the `RedirectFollower` bean (not a second `PublicHttpFetcher` bean, which would break by-type injection).
- **Executors** (`AsyncExecutorConfiguration`): declaring `redirectCheckExecutor` switches off Boot's own `applicationTaskExecutor` and its `@Async` default, so the configuration declares `applicationTaskExecutor` itself from Boot's `ThreadPoolTaskExecutorBuilder` (still `spring.task.execution.*`), also named `taskExecutor` so unqualified `@Async` (emails, `reloadMissing`) and click recording keep using it. `redirectCheckExecutor` (threads `redirect-check-1`, `-2`) waits up to 15 s on shutdown for running checks. `notificationTaskExecutor` (threads `notification-task-1` to `-4`, a 16-task queue) runs the long notification jobs: the nightly destination check and its dead-link notices, the delivery drain and the daily and weekly summaries. It has no shutdown wait of its own; a job cut short by a redeploy is safe to lose (a drain's `SENDING` rows go back to `PENDING` after 10 minutes, the check's unprobed links come first the next night, and the summaries and notices are deduplicated). `applicationTaskExecutor` (unbounded queue) waits up to 10 s on shutdown for its running and queued tasks (`spring.task.execution.shutdown.await-termination` and `await-termination-period` in `application.yaml`, which Boot's builder applies), so the clicks still queued when a redeploy stops the container are recorded; Boot's default would cancel the queue and interrupt the running ones. The wait runs when the beans are destroyed, after `LettuceConnectionFactory` has stopped (lifecycle phase 0) but before the connection pool closes, so a click recorded then takes the Redis-down path and counts as a new unique visitor.

### Discord alerts
An owner-facing alert channel next to the emails, which stay as they are: hrva.cc pings one Discord webhook (created by the owner, set in `DISCORD_WEBHOOK_URL`) when something needs the admin's attention. Blank means off: no buffering, no HTTP calls, and one startup line "Discord alerts are off: no DISCORD_WEBHOOK_URL".
- **Events** (`service/alert/AdminAlertEvent`, published with `ApplicationEventPublisher` at the chokepoints and taken by one listener, `DefaultDiscordAlertService`, through `@TransactionalEventListener(fallbackExecution = true)`, so nothing goes out for a rolled-back change):
  - a review newly opened (`DefaultReviewQueueService`: a flag from link creation, a redirect check, the Safe Browsing recheck or the nightly scan, or a visitor report that opens one). New reasons on an open review don't alert, except a visitor report that adds a line to it; a repeat of a report the entry already holds, or one past the 20-report cap, doesn't.
  - a link blocked automatically (`DefaultModerationService.blockAndTellOwner`, where the owner is emailed, when `performedBy` is `system`: the click check, the nightly scan and Safe Browsing recheck, the redirect check). The admin's own blocks (Block link, Block domain or a Block rule, Block user, from the dashboard or MCP) never alert.
  - a new account (`DefaultUserService.register`, `OAuth2LoginSuccessHandler`).
  - a bio page review (`DefaultBioPageReviewService`, see Bio pages): opened by the text check (`New bio page review: hrva.cc/@ana (name imitates paypal), account #7, <https://app.hrva.cc/admin/review?bio=12>`), opened by a visitor report (`New bio page review from a visitor report: hrva.cc/@ana (spam: "fake shop"), …`), or a visitor report that adds a line to an open one (`Visitor report on an open bio page review: …`). A page without a handle reads `a bio page without a handle (#12)`. Reasons and the visitor's details are shown in full, not cut at 200 characters. An admin hiding a page never alerts, like the admin's link blocks.
  - a blocklist source whose `lastError` goes from none to some ("HaGeZi Fake failed to load: main: HTTP 503", "(a fallback loaded)" when a fallback still stored the list) or back to none ("HaGeZi Fake loads again"), never on a repeated failure (`BlocklistRefresher`).
  - a burst of new links to a new domain (`BurstDetected`, from `DefaultBurstAlertService`, see Burst alert).
  - custom domains: an application, a domain turned off, one that needs attention, and reconcile drift (see Custom domains, ruling 18).
- **Delivery**: the listener only buffers (200 at most; the rest are counted as dropped). `flush` (every 30 s, and `@PreDestroy` on shutdown, since a redeploy restarts the single container) drains the buffer into one message through `DiscordWebhookClient` (`java.net.http`, each call capped at 5 s). A message holds at most 10 lines and 2,000 characters (inclusive). When the batch is longer, the room for the overflow line is kept first, then each line goes in, in order, if it still fits; the rest, plus the dropped count, becomes `and N more, see <{frontendUrl}/admin/review>` and is not carried over. So one alert too long for a message is counted there, never cut, and never hides the alerts after it. The weekly digest doesn't use this buffer (see Weekly digest). Fire and forget: on failure one warn line with the exception class or HTTP status (never the webhook URL), and the batch is dropped, except a send interrupted mid-call (the scheduler stopping on shutdown), whose alerts go back into the buffer, within its cap, for the shutdown flush. Only an HTTP 429 with `retry_after` under 10 s is retried, once, and never on shutdown, so shutdown waits at most 5 s.
- **Payload** (`DiscordAlertFormatter`): `content` only, one plain line per item, with `"allowed_mentions": {"parse": []}` (a visitor's `@everyone` can't ping) and `"flags": 4` (suppress embeds, so Discord never previews a destination; it would hide embeds too, hence no embeds). A link shows as `hrva.cc/<alias> → <destination host>` (never the path or query; an IP destination is "an IP address"), its reasons, `anonymous` or `account #<id>`, and the admin page: `/admin/review?entry=<urlId>` for reviews, `/admin/urls` for blocks, `/admin` for new accounts, `/admin/blocklists` for sources. A burst reads `Possible phishing wave: 5 new links to evil-login.com in the last hour, from 2 different accounts or networks. The domain was registered 4 days ago. Nothing was blocked. Review them: <{frontendUrl}/admin/urls?search=evil-login.com>` (`The domain's age is unknown.` or `The domain was registered today.` when so, `1 day ago` in the singular; the window in whole hours, minutes or seconds, `in the last hour` or `in the last 30 minutes`; "accounts or networks" because a link made without an account counts its network as the creator); an international domain shows both forms, `čokolada.hr (xn--okolada-i6a.hr)`, and the link searches the readable form, URL-encoded. Every value (aliases, hosts, reasons, visitor details, block details, source names, errors) is shown in full, never cut with "…". Free text (visitor details, reasons, block details, errors) loses newlines, backticks, `<>` and `[text](url)` link syntax, gets Discord markdown escaped and web addresses wrapped in `<…>`; email addresses and IP addresses become "(email removed)" and "(IP removed)". Never an email address: a new account is its id and sign-up method (email, Google, GitHub).
- Tests: `service/alert/DiscordAlertFormatterTest` (payload rules, values in full, the 2,000/2,001-character boundary, every line that fits, the burst line and the weekly digest, `bioPageTextIsEscaped`), `client/DiscordWebhookClientTest` (a local `HttpServer`: refusals, 429, timeouts, nothing secret in the log), `service/DefaultDiscordAlertServiceTest` (off when blank, buffer cap, after-commit only, shutdown flush, end to end against a local webhook), and the publisher tests in `DefaultReviewQueueServiceTest`, `DefaultModerationServiceTest`, `DefaultBlocklistSourceServiceTest`, `DefaultUserServiceTest`, `OAuth2LoginSuccessHandlerTest`.

### Weekly digest
A summary of last week for the owner (`DefaultWeeklyDigestService`, `service/digest/`). It is operator mail like the decisions email: it goes only to the owner's Discord webhook and `app.contact-email`, never to a user.
- **When**: Mondays at 08:00 in `app.analytics.zone` (see Scheduled Tasks), for the last closed Monday–Sunday in that zone (`DigestWeek.lastClosedBefore(today)`; run on a Sunday, it reports the week before), compared with the week before (`previous()`). Each week is a `StatsDays.window(from, to)`, so a week across a clock change is still 7 Zagreb days (19–25 October 2026 is stored as `2026-10-18T22:00` to `2026-10-25T23:00`).
- **Content** (`collect`: the four `AdminStatsService` date variants for the week, and traffic, links and users for the week before; the wording is `WeeklyDigestText`): the title `hrva.cc weekly summary: 19–25 October 2026` (`26 October – 1 November 2026` across months), then:
  - clicks; `Visitors: 950 (each link's daily visitors, added up)`; and `Bots and link previews: 20.0% of all clicks`, the bot share of clicks plus bots (one decimal, or `Bots and link previews: no clicks`)
  - new links, and how they were made (left out when there are none)
  - new users, and active users: accounts signed in during the last 7 days before the send (`UsersStatsResponse.activeLast7Days`; `last_login` keeps only the latest sign-in, so a count for the closed week can't be made)
  - reviews opened and resolved, then `Review queue: 3 waiting <{frontendUrl}/admin/review>`: the open reviews at the time of collecting (`SafetyStatsResponse.openReviews`, the Safety tab's open count), not a figure for the closed week
  - automatic blocks: every block reason outside `BlockReason.MANUAL` (`ADMIN`, `USER_BLOCKED`), counting links still blocked by `blocked_at`, like the Safety tab
  - the top 5 links by clicks (`hrva.cc/menu → example.com, 120 clicks`), never the owner; an IP destination reads `an IP address`, a blank one `an unreadable destination`

  Clicks, new links and new users each carry a change: `same as the week before` when equal, `none the week before` when the week before was 0, the week before's own number when it was 1 to 19 (`New users: 3 (1 the week before)`: a percentage of a small number misleads), and from 20 on a percentage, `up 12% on the week before` or `down 5% on the week before` (at least 1%; a drop reads at most 99% unless it fell to 0, so `down 100%` always means none), never a division by zero. Numbers are English (`1,204`) whatever the server locale. There is no QR or direct figure.
- **Once a week**: after collecting, so a database failure throws before the week is used up, `SET digest:weekly:<Monday> <now> NX` with an 8-day TTL. Already set → `Weekly digest already sent week=<Monday>` and nothing is sent. Redis down → one warn line `Weekly digest skipped: Redis is unavailable, so it can't make sure it is sent once exception=<class>` and nothing is sent: a missed week is better than a double post. No retry and no catch-up after downtime.
- **Delivery**: `sendWeeklyDigest` runs with `propagation = NOT_SUPPORTED`, so no database connection is held through the Redis claim or the Discord call; each stats read has its own read-only transaction.
  - Discord: straight through `DiscordWebhookClient.send(…, 5 s)`, never through the 30-second alert buffer, which holds 10 one-line alerts. One message (`DiscordAlertFormatter.weeklyDigest`) with the alert rules: no mentions or embeds, markdown escaped, hosts only, values in full. Links are wrapped in `<…>` (the review queue line too) and it ends with `Stats (last 7 days): <{frontendUrl}/admin/dashboard?days=7>` (that page shows the rolling 7 days, not the closed week). Over 2,000 characters, top links are dropped from the end and `and N more` takes their place; the links are ranked, so none is skipped to fit a later one.
  - Email (`SendingEmailService.sendWeeklyDigestToAdmin`, `@Async`, through `tryToSendEmail`, so the email log records it): to `app.contact-email`, subject the title, as `multipart/alternative` with the plain text (the title, the lines and the stats link; links bare, as in `Review queue: 3 waiting https://…/admin/review`) and `weekly_digest.html` (`th:text` escapes every value; the summary comes as `WeeklyDigestText.Line`s, so the review queue's address is a real link, and the button reads `Open stats (last 7 days)`). The log keeps the HTML only, so a resend sends the HTML only.
  - A failure of one never stops the other. The run ends with `Weekly digest sent week=<Monday> discord=<posted> email=<queued>`: `email=true` means the email was queued, not delivered; an SMTP failure lands in the email log as `FAILED`, its HTML kept for a resend. The webhook URL is never logged.
- **Switches**: `app.digest.weekly.enabled` (Discord, which also needs `DISCORD_WEBHOOK_URL`) and `app.digest.weekly.email`, both on by default and independent (see Config Profiles). With both off, or Discord on with a blank webhook and the email off, the job logs `Weekly digest is off` and reads nothing.
- Tests: `service/digest/DigestWeekTest` (every day of 2025–2027, both clock changes, the new year), `WeeklyDigestTextTest`, `service/DefaultWeeklyDigestServiceTest` (once a week, the key and its TTL, Redis down, the switches, one delivery failing, no transaction while sending), `DefaultEmailServiceTest`, `DefaultSendingEmailServiceTest`, `DefaultScheduledServiceTest` (the cron and zone), `model/enums/BlockReasonTest`.

### Burst alert
A phishing-wave alert for the admin (`DefaultBurstAlertService`, `service/burst/`): many new links to one new domain from several creators in a short time. It only alerts; nothing is blocked.
- **Rule**: at least `app.burst.links` (default 5) distinct new links from at least 2 creators within `app.burst.window` (default 1 hour) to one registrable domain that is under 30 days old or of unknown age (`DomainAgeService.registeredOn` empty counts as new; `.de` and `.hr` registries give no dates). One alert per domain per 24 hours.
- **What counts**: every saved link, each bulk item included, from the web, API keys, bulk and MCP. An `ALLOWED` verdict (an Allow rule) is never counted, and a Block never saves a link. The domain is `DomainNames.registrableDomain` of the ASCII host, so `a.evil.com` and `b.evil.com` share a count while `x.github.io` and `y.github.io` don't; IP and unreadable hosts are skipped, as they're already flagged for review.
- **Creators** (`CreatedLink.creatorOf`): `user:<id>`, or for a link without an account `RateLimiter.clientKey("anonymous", ip)` (`anonymous:<sha256 of the IPv4 address or IPv6 /64>`, never a raw IP). An API-key link counts as its owner. So one owner's batch, or many anonymous links from one network, is one creator and never alerts.
- **Counting** (`RedisBurstCounter`, one Lua script on `burst:links:<domain>`): `ZADD` the member `<urlId>|<creator>` at now, `ZREMRANGEBYSCORE` what is older than the window, `PEXPIRE` the window, `ZRANGE`. Links are the distinct url ids and creators the distinct parts after the first `|`, so a reused anonymous link is one link (from two networks, two creators).
- **Order**: the count; then `burst:alerted:<domain>` (present → stop, before any RDAP call); then the domain age; then `SET burst:alerted:<domain> 1 NX` for 24 hours. Only the caller that wins that `SET` publishes `AdminAlertEvent.BurstDetected(domain, links, creators, domainAgeDays, window)` and logs `Burst of new links domain=<domain> links=<n> creators=<n> ageDays=<n or null>`. The event goes through the 30-second Discord buffer like the other alerts (its line: see Discord alerts), and its link `/admin/urls?search=<readable domain>` lists the links under either spelling of the domain (see Abuse handling, Search terms).
- **Timing and failures**: `DefaultUrlService.reportCreated` hands `linkCreated` a `CreatedLink(urlId, longUrl, creator, outcome)` right after `checkRedirectsLater`, outside the create's transaction, and the check runs `@Async` on `applicationTaskExecutor`, so neither RDAP (3 s) nor Redis can slow or fail a create. A failure to hand it over logs `Could not schedule the burst check urlId=<id> exception=<class>`; any failure in the check (Redis down, RDAP) logs one `Burst check skipped domain=<domain> exception=<class>` and alerts nothing. The service has no transaction, as it never touches the database.
- **Properties**: `app.burst.links` (at least 2) and `app.burst.window` (at least 1 second: the alert names the window in whole seconds, so a shorter one would read "in the last 0 seconds"), both checked at startup (see Config Profiles).
- Tests: `service/burst/CreatedLinkTest`, `RedisBurstCounterTest`, `service/DefaultBurstAlertServiceTest` (thresholds and edges, one owner or network, old and unknown ages, once a day and lost races, Redis down, international hosts, the async proxy), `UrlServiceTest` (who is reported, a failing check never fails the create), `AppPropertiesTest`.

### Public numbers
`GET /api/v1/public/stats` (`PublicStatsController` → `DefaultPublicStatsService` → `service/stats/PublicStats`) feeds the frontend's public "hrva.cc in numbers" page (`/stats`). Aggregates only: the answer has no alias, host, email, country, referrer or any other per-link or per-person field, and nothing reads an IP address, User-Agent or referrer URL.
- **Window**: the 30 full days ending yesterday in `app.analytics.zone` (`StatsDays.window(from, to)`). Closed days don't change, so the hourly cache is honest.
- **Fields** (`PublicStatsResponse`):
  - `from`, `to`, and `updatedAt` (`storedNow()`)
  - `activeLinks`: links active now (`countInventory(storedNow())`)
  - `linksCreated`: in the window
  - `clicks` and `daily`: human clicks only, `daily` zero-filled to 30 days
  - `blocked.allTime`: links still blocked, any reason; `blocked.last30Days`: blocks in the window by `blocked_at`, from the hourly block counts. Links refused at creation were never saved and aren't counted.
  - `visitorReportsHandled`: reviews resolved in the window whose reasons contain `reported by a visitor` (`SafetyStatsRepository.countResolvedVisitorReports`)
  - `averageReviewMinutes`: the mean of the window's resolve times, rounded to whole minutes, `null` without any
  - `blocklists`: enabled sources with a loaded `domain_count` above 0, giving only the name, action and entries (never the URL or error), most entries first, then by name. Read from `blocklist_source` alone (`findByEnabledTrue`), so there is no Redis read per source. The names are public, so keep them presentable.
- **Caching**: the JSON (the app's `JsonMapper`) in Redis under `public:stats` for 1 hour. A miss, unreadable JSON or a Redis failure computes it (`Public stats cache read failed, computing them exception=<class>`); a failed write is logged (`Public stats cache write failed exception=<class>`) and ignored. Only `PublicStats.collect()` has a read-only transaction, so a cache hit holds no database connection. A 200 carries `Cache-Control: max-age=600, public`. Redis down → computed on every request, still 200.
- **Rate limit**: 60 per hour per network (`RateLimiter.clientKey("public-stats", ip)`). Over it → 429 `You've opened these numbers a lot in a short time. Try again in an hour.` Limiter down → allowed, with `Public stats rate limit unavailable, allowing the request`.
- **Security**: `/api/v1/public/**` is `permitAll` for every method in the API chain (the same line link-in-bio adds, so a merge keeps one), so a stale token never breaks the page; `POST` and `DELETE` get 405 `Allow: GET`, and other paths 404.
- Tests: `service/stats/PublicStatsTest` (the window, every definition, a fresh site all zeros, the record shape), `service/DefaultPublicStatsServiceTest`, `controller/PublicStatsControllerTest`, `PublicStatsEndpointSecurityTest`, `repository/stats/SafetyStatsRepositoryTest`.

### Passkeys (WebAuthn) (`passkey_credential` and `passkey_sign_in_daily` tables, migration `028-passkeys-and-two-step.xml`)
Any account can add any number of WebAuthn authenticators (passkeys on a phone or computer, in a password manager, or on a hardware security key), sign in with them without a password, and use them as the second step. Verification is Spring Security 7.1.1's `Webauthn4JRelyingPartyOperations` (`spring-security-webauthn`, webauthn4j 0.31.9) over our own tables through two adapters, `JpaUserCredentialRepository` (Spring's `UserCredentialRepository`) and `JpaPublicKeyCredentialUserEntityRepository`; no session filter and no `webAuthn()` DSL. Code: `service/passkey/`, `PasskeyController`, `PasskeySignInController`, `TwoStepController`, `TwoStepSettingsController`.
- **Tables (028)**:
  - `user_account`: `two_step_enabled` (not null, default false) and `webauthn_user_handle` (unique).
  - `passkey_credential`: `user_id` (foreign key with cascade delete, indexed), `credential_id` (unique), `public_key`, `attestation_object`, `sign_count`, `uv_initialized`, `backup_eligible`, `backup_state`, `discoverable` (the `credProps.rk` result, null when the browser didn't report it), `transports` (comma-separated, null when none), `aaguid` (null when all zeros), `label` (≤ 64), `created_at`, `last_used_at`. Binary values are base64url strings, never `@Lob`: `credential_id` in a `VARCHAR(1400)`, `public_key` and `attestation_object` as `TEXT`. `attestation_object` is kept because `Webauthn4JRelyingPartyOperations.authenticate()` requires it and rebuilds the public key from it.
  - `passkey_sign_in_daily(stat_date, sign_ins)`: passkey sign-ins per day (passwordless and second step), counted with a `MERGE` outside the sign-in transaction; a failed count is logged and never fails the sign-in. Per-login rows are never stored. Collected from the first deploy for the admin Users tab (users with a passkey, total passkeys, sign-ins in range), which a follow-up adds once the admin stats build is on `main`.
- **User handle**: 32 random bytes (`Bytes.random()`), base64url (43 characters), created on the user's first registration options request by a conditional update (set only while null, then re-read), so parallel requests can't end with two handles. It is never the email or the numeric id and appears in no response except as `options.user.id`. `user.name` and `user.displayName` are the email: a changed email doesn't update the name password managers show; sign-in uses the handle.
- **Ceremonies** are stateless REST calls. An options endpoint stores `{"purpose":"SIGN_IN","challenge":"<base64url>","userId":null}` under a random ceremony id in `passkey:ceremony:<ceremonyId>` (5 minutes) and returns `{ceremonyId, options}`. The verify endpoint reads it once with `GETDEL`, checks the purpose (`REGISTRATION`, `SIGN_IN`, `SECOND_STEP`, `TWO_STEP_DISABLE`) and the account, and rebuilds identical options (`PasskeyCeremonies`, `PasskeyOptionsFactory`): the challenge from Redis, `allowCredentials` from the database at verify time, user verification from the purpose. Unknown, expired, used, or for another purpose or account → 410 `This request expired. Try again.`; Redis down → 503 `Passkeys aren't available right now. Try again in a minute.` Ceremony ids and pending tokens are 32 `SecureRandom` bytes, base64url without padding (`SecureTokens.random()`).
- **Options limits**: `/auth/passkeys/options` allows 30 per 10 minutes per network (`rate-limit:passkey-options:<sha256 of the network>`) → 429 `Too many passkey sign-in attempts from this network. Try again in a few minutes.` `/auth/2fa/webauthn/options` has its own key with the same limit (`passkey-second-step-options`): the login page's autofill asks for sign-in options on every load and every 240 s, which behind a shared address could otherwise lock out someone who already passed the password step. Both fail closed (503).
- **Compatibility values (every ceremony)**:
  - RP ID `app.passkeys.rp-id`, RP name the literal `hrva.cc` (never `app.app-name`), origins `app.passkeys.allowed-origins`
  - attestation `none`, no AAGUID allow-list, `authenticatorAttachment` never set
  - algorithms in this order: ES256 (−7), EdDSA (−8), RS256 (−257); `timeout` 300000 ms
  - registration: `residentKey: preferred`, `userVerification: preferred`, extension `credProps: true`, `excludeCredentials` = the user's passkeys with their transports
  - passwordless sign-in: `allowCredentials: []`, `userVerification: required`
  - second step and turning two-step off: `allowCredentials` = the user's passkeys (all kinds), `userVerification: preferred`
  - a sign count of 0, and backup-eligible or backed-up credentials, are always accepted
  - password-manager JSON (`PasskeyJson`): unknown transports such as `cable` are dropped before Spring reads them; a missing `transports`, `authenticatorAttachment: null`, the extra `toJSON()` fields, unknown extension outputs and base64url with `=` padding all register. Unreadable JSON or a missing `response` → 400 `That passkey response couldn't be read. Try again.`
- **Counter rule** (`SignCountPolicy`, checked against `passkey_credential.sign_count` before `authenticate()`): refuse when `presented > 0 && presented <= stored`, logged with the 8-character credential prefix; 0 after 0, and 0 after a non-zero count, pass; the stored count never goes down (`max(stored, presented)`). webauthn4j's own counter check is switched off in `PasskeyConfiguration`, because Spring rebuilds the credential record from the registration-time attestation object and webauthn4j would compare against the registration count. Each verified assertion also refreshes `backup_state` and `last_used_at`.
- **Refusals** (`PasskeyAssertions`): a credential id that isn't registered (deleted between options and verify, or a stale password-manager entry) → 401 `This passkey isn't registered on hrva.cc. Remove it from your password manager or device, or sign in another way.`; any other refusal (library, counter, user handle, another account's passkey at the second step or turn-off, origin) → 401 `That passkey or security key couldn't be verified. Try again.`, never library text. `verify` runs only inside a read-write transaction (`MANDATORY`; a read-only one is refused).
- **Re-auth** (`Reauthentication`) for registration options, remove and `DELETE /users/me`; renaming needs none. Email and password accounts send `{password}` (blank → 400 `Enter your current password.`, wrong → 403 `Current password is incorrect`, 20 wrong on `reauth:<userId>` → 403 `Too many wrong passwords. Try again in 24 hours.`; `PATCH /users/password` shares that counter). Google and GitHub accounts need a JWT whose `iat` is within the last 15 minutes (`RecentSignIn.WINDOW`), otherwise 401 `For your security, sign in again to change your passkeys and security keys.`; deleting the account (`confirmAccountDeletion`) answers 401 `For your security, sign in again to delete your account.` The password goes with the options request, so the browser prompt never opens for a wrong one, and the ceremony is bound to that user id.
- **Labels**: optional, trimmed, at most 64 characters; blank → `Passkey`. A credential that is already registered → 400 `This passkey or security key is already added.`
- **Kinds** (`PasskeyCredential.kind()`, in this order): `discoverable == false` → `SECOND_STEP_ONLY`; backup eligible → `SYNCED`; `discoverable == true` → `DEVICE_BOUND`; otherwise `UNKNOWN`. A second-step-only key works after the password but can't sign in alone.
- **Security notice**: once the registration commits, `PasskeyAddedEmailListener` (`@TransactionalEventListener(phase = AFTER_COMMIT)` on `PasskeyAddedEvent`) emails "A passkey was added to your account" (`passkey_added.html`: the label, the time in UTC such as `25 October 2026 at 14:05 UTC`, links to Settings and `/help/passkeys`, and the contact address). If it wasn't them, email and password accounts are told to remove it and change their password, Google and GitHub accounts to remove it and secure their Google or GitHub account (`local_account` in the template context). A NULL `api_key_slots` renders as 0 and never stops an email. A failed send is logged and never fails the registration.
- **`@DynamicUpdate` on `User`**: updates write only the changed columns, so a save such as `lastLogin` can't write back a stale `two_step_enabled`. It protects managed copies only; a detached `merge` still writes every field that differs, which is why an admin block or reactivation, and the admin user edit, turn `active` with a targeted update (`deactivateById`, `reactivateById`) instead of saving the account they loaded, and a Google or GitHub sign-in records `lastLogin` with `recordLastLogin`.
- **The RP ID can't change once users have passkeys: every passkey is bound to it.**

### ReservedAlias (`reserved_alias` table, migration `027-admin-stats-and-reserved-aliases.xml`)
- `ID`, `ALIAS` (≤ 32, unique constraint `UX_RESERVED_ALIAS_ALIAS`), `REASON` (≤ 200), `CREATED_AT`, `CREATED_BY` (the admin's email), all `NOT NULL`. Aliases are stored trimmed and lower-cased, so the plain unique constraint is the case-insensitive one (a `lower()` index isn't portable Liquibase).
- `ReservedAliasService.isReserved` is the one place that answers "is this alias reserved": exact and case-insensitive after trimming, against the built-in words and the table. The built-in words are the old hardcoded list plus `anon` (since v2.11, so nobody can claim the removed `/mcp/anon` path as an alias), 12 in this order: `actuator`, `anon`, `api`, `auth`, `error`, `login`, `logout`, `mcp`, `oauth2`, `swagger-ui`, `v3` and `webjars`, listed with the reason "Used by hrva.cc itself"; they are never stored and can't be removed. A custom entry is one `existsByAlias` lookup on the unique index, with no in-memory cache, so a reservation applies at once.
- Every create path checks it: a custom alias on the web, with an API key, in bulk or through the signed-in MCP `shorten_url` goes through `checkIfShortUrlIsReserved` → 409 `This short URL is reserved. Try another.` (the admin's reason never leaves the admin endpoints), and random generation (`nextFreeShortUrl`, also for anonymous links) tries up to 10 candidates, skipping reserved and taken ones, then → 409 `Couldn't pick a free short URL. Try again.` Aliases can't be edited (`UrlUpdateDto` has no `shortUrl`); an alias edit, if ever added, must call the same check.
- Reserving and removing are audited by `DefaultReservedAliasService` with the alias as the target and `reason: …` as details, a refused reservation too (see AuditLog).
- Reserving refuses a duplicate, a built-in word or a lost insert race (`DataIntegrityViolationException`) with 409 `This alias is already reserved.` The alias is validated like a custom alias: the FE trims it before sending, and the API refuses one with spaces with the pattern message on purpose, as it does for a custom alias.
- Revoking a bio page handle (admin) reserves it with the reason `Revoked bio page handle: <reason>`, cut to 200 on whole characters and attributed to that admin; removing the entry lets anyone take the handle again.
- `inUse` lists the links that already hold the alias, in any case (`UrlRepository.findByLowerShortUrlIn`, one query for the whole list). Reserving such an alias leaves those links working; nothing is deactivated.

### Unique short URLs (`UX_URL_SHORT_URL`, migrations 027 and 030; `UX_URL_DOMAIN_SHORT_URL`, migration 032)
- Since 032 an alias is unique per domain: `032-url-domain-short-url-unique` creates `ux_url_domain_short_url (domain_id, short_url)` with `NULLS NOT DISTINCT` (skipped, `MARK_RAN`, when an alias already repeats within a domain), and `032-url-short-url-unique-dropped` drops `UX_URL_SHORT_URL`. `ShortUrlUniqueIndex` follows the new index (see Custom domains, ruling 2); the rest of this section describes 027 and 030 as they ran.
- `Url.shortUrl` was always `@Column(unique = true)`, but Liquibase never created the index. `027-url-short-url-unique` creates the unique index `UX_URL_SHORT_URL` on `URL(SHORT_URL)` (case as stored) behind a `sqlCheck` precondition with `onFail="MARK_RAN"`: a database that already holds duplicate short URLs marks it ran and skips the index instead of failing Liquibase, and with it the startup of the only container. Its rollback is `drop index if exists`, so it also rolls back where it was skipped.
- Production held one duplicate, so 027 was `MARK_RAN` there; `030-url-short-url-unique-again.xml` (v2.13) enforces the index anyway, in two changesets:
  - `030-url-short-url-rename-duplicates`: for each `short_url` held by more than one row, the row `findFirstByShortUrlOrderByActiveDescIdDesc` serves (active first, then the highest id; `row_number() over (partition by short_url order by active desc, id desc)`, so the database's own ordering decides, as in the lookup) keeps its alias and every other row becomes `alias~id`. `~` is never valid in an alias (`CreateUrlDto` and `ReservedAliasDto` allow `[a-zA-Z0-9_-]`, generated aliases are alphanumeric), so a renamed alias can't clash with a real one. The alias part is cut to `254 - length(id)` characters, so the result always fits `VARCHAR(255)`. Plain SQL on Postgres and H2; with no duplicates (production since the owner renamed row 222 by hand) it updates nothing. Its rollback is empty. The renamed rows were never served, so nothing is evicted from the `urls` cache: the cache entry under the alias is already the served row's.
  - `030-url-short-url-unique`: creates `UX_URL_SHORT_URL` unique on `URL(SHORT_URL)` unless an index of that name exists, matched case-insensitively (`pg_indexes` on Postgres, `information_schema.indexes` elsewhere), so a database where 027 ran, or where the owner made `ux_url_short_url` by hand, is `MARK_RAN` and gets no second index. Its rollback is empty: the index is harmless without duplicates, and 027 may own it.
- `ShortUrlUniqueIndex.enforced()` reads `databasechangelog`: true when `027-url-short-url-unique` is `EXECUTED` or `030-url-short-url-unique` is `EXECUTED` or `MARK_RAN`; no such row or a database error → false. When it isn't enforced (only before 030 runs), startup logs once `short_url uniqueness not enforced: duplicate short URLs exist, so 027-url-short-url-unique was skipped`, and the System tab shows `database.shortUrlUnique: false`.
- A create that loses an alias race to a concurrent one now fails on the index: `insertNewLink` saves and flushes (`Url` ids come from a sequence, so a plain `save` would only insert at commit), and a `DataIntegrityViolationException` that `ShortUrlUniqueIndex.violatedBy` matches to `UX_URL_SHORT_URL` becomes 409, `This short URL is already taken. Try another.` for a custom alias or `Couldn't pick a free short URL. Try again.` for a generated one, instead of a 500. Any other integrity violation is rethrown. The flush runs before the link is cached, so the request that lost never caches its destination under the winner's alias.
- 027 has nine changesets: the five range indexes (`IDX_LINK_DAILY_STATS_STAT_DATE`, `IDX_LINK_DAILY_BREAKDOWN_DATE_DIMENSION`, `IDX_URL_CREATE_DATE`, `IDX_USER_ACCOUNT_CREATE_DATE`, `IDX_LINK_REVIEW_FLAGGED_AT`), `027-url-created-via`, `027-url-short-url-unique`, `027-reserved-alias` and `027-url-long-url-length` (`URL.LONG_URL` from `VARCHAR(255)` to `VARCHAR(2048)`, still `NOT NULL`; its rollback is empty, because a wider column is harmless and narrowing it would fail on longer rows).

### Bio pages (`bio_page`, `bio_page_button`, `bio_handle_hold`, `bio_page_daily_views`, `bio_page_review` tables, migration `029-link-in-bio.xml`)
Every account can publish one page at `hrva.cc/@handle`: a display name, a short bio, an initials or emoji avatar, an accent and theme, and an ordered list of buttons that are the owner's own short links. Code: `service/bio/`, `DefaultBioPageService` (owner), `DefaultPublicBioPageService` (public read and views), `DefaultBioPageAnalyticsService`, `DefaultBioPageReviewService`, `DefaultAdminBioPageService`, and the controllers `BioPageController`, `PublicBioPageController`, `BioRedirectController`, `AdminBioPageController`, `AdminBioPageReviewController`. Endpoints: see Key Endpoints.
- **Tables (029)**:
  - `bio_page`: `user_id` (unique, cascade from `user_account`), `handle` (≤ 30, unique, null after a revoke), `display_name` (≤ 50), `bio` (≤ 160), `avatar_kind`, `avatar_emoji` (≤ 16), `accent`, `theme`, `indexable`, `hidden_at`, `hidden_reason`, `hidden_by` (the admin's email), `handle_revoked_reason`, `created_at`, `updated_at` (both truncated to microseconds when written; see Saving).
  - `bio_page_button`: `page_id` and `url_id` (both cascade; unique together as `uq_bio_page_button_page_url`, so a link is on a page once), `title` (≤ 60), `icon`, `sort_order`, `visible`. Deleting a link deletes its buttons.
  - `bio_handle_hold`: `handle` (the key), `page_id` (`SET NULL` when the page goes), `held_until`, `created_at`.
  - `bio_page_daily_views(page_id, stat_date, views, bot_views)`, cascade from the page.
  - `bio_page_review`: `page_id` (cascade, `fk_bio_page_review_page`), `reasons` (newline-joined), `flagged_at`, `resolved_at`, `resolved_by`, `resolution` (`OK`, `HIDDEN`), `system_flagged`.
  - Enums are stored by name: avatar `INITIALS` or `EMOJI`, accents `BLUE`, `VIOLET`, `PINK`, `RED`, `ORANGE`, `GREEN`, `TEAL`, `SLATE`, themes `AUTO`, `LIGHT`, `DARK`, and 12 icons from `WEBSITE` to `TELEGRAM`. Lengths count UTF-16 units: handle 3–30, name 50, bio 160, title 1–60, emoji 16, at most 30 buttons.
- **Handles** (`BioHandles`): stripped, one leading `@` removed, lower-cased (`Locale.ROOT`), then 3–30 of `[a-z0-9_-]` with at least one letter or number (400 `A handle must be 3 to 30 characters.`, `Use only letters, numbers, hyphens and underscores.`, `A handle needs at least one letter or number.`). 409 `This handle is reserved. Try another.` for a reserved alias (`ReservedAliasService.isReserved`), one of `BioHandles.SYSTEM_WORDS` (`abuse`, `admin`, `api`, `help`, `hrva`, `login`, `support`, `www` and the rest), or a first part (split on `-` and `_`, empty parts skipped) of `hrva`, `hrvacc` or `hrvalabs`, so `hrva-support` and `_hrva` are refused and `hrvatska` isn't. 409 `This handle is taken. Try another.` for another page's handle, a live hold for another page, or a lost race. A live hold for no page (a deleted page or account) → 409 `This handle was recently used and is kept until November 25, 2026. Try another.`, the date being the hold's `held_until` in English (`MMMM d, yyyy`, `Locale.ENGLISH`, whatever the server's locale); the availability check gives the same reason. Handles and short-link aliases are separate namespaces (`/@x` and `/x`). A create or the owner's handle change checks the format, then availability, writes and flushes, and only then spends the 5-a-day handle budget, inside the same transaction: a refused handle or a lost race spends nothing, and a change over the budget is a 429 that rolls back.
- **Holds**: a rename, by the owner or an admin, holds the old handle 30 days for that page, which may take it back (the hold is deleted). Deleting a page or the account holds its handle 30 days for nobody (`page_id` null), so its former owner can't take it back either (nothing records who held it) and is told until when. An old handle shows "This page isn't available." and never redirects to the new one. The 03:45 job deletes expired holds (see Scheduled Tasks).
- **The page lock** (`BioPageLock`, like passkeys' `AccountLock`): every write on a page reads it, locks its row with `BioPageRepository.findByIdForUpdate` (`PESSIMISTIC_WRITE`, which Hibernate 7.4 runs on Postgres as `select … from bio_page bp1_0 where bp1_0.id=$1 for no key update of bp1_0`) and re-reads it (`refresh`), inside a write transaction (`MANDATORY`; a read-only one is refused). The owner's save, handle change and delete take it, so do every admin write (hide, unhide, rename, revoke, both resolves) and account deletion (`BioAccountData.deleteFor`); reads (`mine`, availability, the public read, analytics) don't. So two saves take turns (the second updates the first's buttons in place and answers 200, or 409 when it sends the `expectedUpdatedAt` both started from), a save after a delete is a 404, a delete after a save deletes, and nobody writes back a stale row (`BioPage` has no `@DynamicUpdate`). A save holds the lock for about 20 ms. An insert that references the page (the first view of a day, a new review) takes `FOR KEY SHARE` on its row, which doesn't conflict with `FOR NO KEY UPDATE`, so views and reports never wait for a save; they do wait for a page delete (`FOR UPDATE`), and then fail the foreign key (see Review queue).
- **Every 409 on a bio page** (`BioHandleUnavailableException` or `BioPageConflictException`):
  - create: `You already have a bio page.` when the caller has a page, or lost the insert race on `uq_bio_page_user_id` (`create` runs `NOT_SUPPORTED`: its insert and the handle budget commit on their own, in one `TransactionOperations` transaction, so the follow-up read gets a fresh transaction on Postgres, where a failed statement aborts the transaction)
  - create, handle change, admin rename: `This handle is reserved. Try another.`, `This handle is taken. Try another.` (also a lost race on `uq_bio_page_handle` or `pk_bio_handle_hold`), or `This handle was recently used and is kept until <date>. Try another.`
  - save: `Your bio page changed in another tab or window. We loaded the latest version; check your changes and save again.` when `expectedUpdatedAt` isn't the stored `updated_at`
  - save: `This page changed. Reload and try again.` when a link is deleted before the save (`findAllById` doesn't return its id; someone else's or an anonymous link stays 400 `You can only add your own short links.`, checked first) or during it: a new button's insert hits `fk_bio_page_button_url`, or a kept button's update finds 0 rows; the `uq_bio_page_button_page_url` catch stays as a net
  - delete: `An admin hid this page, so it can't be deleted here. You can still delete your whole account in Settings.`
  - admin revoke: `This handle changed. Reload and try again.` when `expectedHandle` isn't the current handle
  - a second delete that raced the first is a 404 `You don't have a bio page yet.`
- **Saving** (`PUT /me`): save rate limit → lock → the copy check (`expectedUpdatedAt` against the `updated_at` just read under the lock, both truncated to microseconds; a mismatch → 409 before any 400; left out, the save is accepted and one info line `Bio page save sent without expectedUpdatedAt pageId=N` is logged, with no personal data, to show whether any client still skips it) → clean the name, bio and titles → avatar → buttons (distinct ids, own links through one `findAllById`, where an id it doesn't return is a deleted link and a 409, a newly added link `LIVE` or `IN_REVIEW`) → reconcile by `urlId` (matching rows updated in place, keeping their ids for analytics; removed rows `deleteAllInBatch` and flushed before new rows are inserted) → `saveAndFlush`. Nothing is written before every check passes, and existing buttons whose links stopped working stay saveable. `indexable` and `visible` are `Boolean` in the request (Jackson 3 refuses a missing primitive): left out means not indexable and visible. Text signals run only after a successful write.
- **`updated_at` and the copy check**: `updated_at` is truncated to microseconds wherever it's written (`BioPage.micros` in `@PrePersist`, `@PreUpdate` and the save's explicit set; `BioPageTest` checks `micros` with a nanosecond value, because the macOS clock already stops at microseconds), so the value a create, save or handle change returns is what Postgres stores (`timestamp`, microseconds) and what a later `GET /me` returns, and a save that sends the previous answer's `updatedAt` never gets a 409. `@PreUpdate` is the writer whose value reaches the row: it overwrites the explicit set at `saveAndFlush`. The explicit set in `update` exists so a save that changes only buttons (separate `bio_page_button` rows) still dirties `BioPage`, fires `@PreUpdate` and bumps `updated_at`; without it a tab holding the copy from before that save could overwrite it (`BioPageOwnerFlowTest.aSaveFromBeforeASaveThatChangedOnlyAButtonIs409` fails when the set is removed). The owner's own handle change and every admin write (hide, unhide, rename, revoke, resolve with `HIDE`) bump it, so an owner's save from a copy older than one of them is a 409; the editor then refetches, rebases the draft over the new page and sends the new `updatedAt`. Jackson writes `updatedAt` as an ISO local date-time with 0–6 fraction digits (trailing zeros dropped) and reads `expectedUpdatedAt` the same way. Like `updated_at` (the JVM zone, UTC in the container), a hold's times are UTC, from the injected `Clock.systemUTC()`, so the recently-used hold date (`kept until <date>`) is formatted from the UTC `heldUntil`: the UTC day the hold ends.
- **Text cleaning** (`BioPageText.clean` for the name and titles, `BioPageText.cleanBio` for the bio): removes `[\p{Cc}&&[^\s]]`, every `\p{Cf}` except ZWNJ, ZWJ and tag characters, and U+115F, U+1160, U+3164, U+FFA0 and U+2065; normalises to NFC; caps a run of `\p{Mn}`/`\p{Me}` marks (format characters between them don't break the run) at 4, which keeps Hebrew cantillation and blocks zalgo. The name and titles then collapse `[\s\p{Z}]+` to one space and strip. The bio keeps line breaks instead (the FE's `cleanBioText` gives the same output): `\r\n` and a lone `\r` become `\n`; in each line, runs of `[\s\p{Z}]` other than `\n` (tabs, NBSP, U+2028, U+2029, …) become one space and the line is stripped; a line with no visible code point (as below, so also one holding only a ZWJ, a lone mark or U+2800) is dropped, which removes blank lines and leading and trailing breaks; at most 5 lines stay, and lines 5 onward are joined with single spaces. A `\n` counts as one toward the 160. Text with no visible code point (only marks, format characters, spaces, U+2800 BRAILLE PATTERN BLANK or U+FFFC OBJECT REPLACEMENT CHARACTER) becomes empty, so such a title is `Give the button a title` and such a name is stored empty; both characters stay beside real text. Lengths are checked again after cleaning (NFC can grow text), and text is refused, never cut. HTML and URLs stay inert text. An emoji avatar is one grapheme, at most 16 units, whose first code point is above U+007F and `Character.isEmoji`, and which neither starts nor ends with ZWJ or ZWNJ (`Pick one emoji for the avatar.`); `INITIALS` clears it. Tests and sources build invisible characters from code points, never raw.
- **Which buttons show** (`BioLinkStates.of`, in order): a block reason or threat type → `BLOCKED`; inactive → `LIMIT_REACHED` at its visit limit, `EXPIRED` past its expiry, else `DEACTIVATED`; active but past its expiry → `EXPIRED`; active but at its limit → `LIMIT_REACHED`; an open `system_flagged` link review → `IN_REVIEW`; otherwise `LIVE`. A button shows only when it is visible and `LIVE`; a visitor report alone never hides one. A page is public when it has a handle, isn't hidden and its owner's `active` isn't false; every other case is the same 404, and nothing caches the page (`no-store`; the FE renders it per request).
- **The redirect** (`BioRedirectController`, `/@{handle:.+}`): 302 to `{frontendUrl}/bio/<handle>`, lower-cased and path-encoded, the query string dropped. It never looks the page up, so it leaks nothing and can't redirect elsewhere.
- **Views**: the FE page sends `POST /api/v1/public/bio-pages/{handle}/views` once per load, with no body (a simple request). It answers 204 whatever happens and counts nothing for a page that isn't public. Then `rate-limit:bio-view:<sha256 of the network>` allows 60 a minute (over it the view isn't counted; Redis down counts it with one warn line and no IP). A bot (`UserAgentClassifier`, a blank User-Agent included) adds one `bot_views` every time; a human adds one `views` only as a new visitor of the day (`UniqueVisitorCounter.isNewBioPageVisitor`, see Click analytics). The owner's own visits count. The day is `AnalyticsDays.today()`. `BioPageViewStatsRepository.increment` is the portable `MERGE`, retried once, and `NOT_SUPPORTED` on the method itself, so it commits on its own (Postgres would refuse it inside the read-only transaction). No IP, User-Agent or hash is stored or logged.
- **Analytics** (`GET /api/v1/analytics/bio-page`): `days` is checked first (400 `days must be 7, 30, 90 or 365`), then the caller's page (404). `daily` is zero-filled to `days` entries and the totals are its sums. Per button, `visible` is the button's own switch and `linkState` its link's `BioLinkStates.of` value, the editor's (`LIVE` for a working link), so the FE can say why a button isn't on the page (`shownOnPage` is visible and `LIVE`); `fromHrvaPages` is the link's `REFERRER` breakdown for `ReferrerClassifier.ownHost()` (the server host, which the frontend host maps to, so clicks from `app.hrva.cc/bio/…` count) and `allClicks` its `CLICKS`, both over the range from `LinkStatsRepository.sumReferrerClicksByUrl` and `sumClicksByUrl`; there is no new click tracking. Locally `app.server-url` is `http://localhost:8080`, whose host `localhost` has no dot, so clicks from `http://localhost:3000/bio/…` are `other` and `fromHrvaPages` stays 0.
- **Review queue** (`bio_page_review`, its own queue because `link_review` is keyed to links throughout):
  - `flag` (the text signals after a create, save or handle change): skipped for a hidden page; extends the open review quietly, or opens one with `system_flagged` and alerts, unless the newest review was resolved `OK` with every incoming reason.
  - `report` (`POST /api/v1/reports` with a bio page target, public pages only, the shared `report` limit): adds `reported by a visitor: <category>[: details]`, at most 20 report lines per review, and alerts when it added a line or opened a review. A report never hides anything. A report racing an account deletion, or the owner's own `DELETE /api/v1/bio-pages/me` (the same `ON DELETE CASCADE`), fails one of two ways: opening a review fails on `fk_bio_page_review_page`, and extending an open review finds its row already cascaded away (a 0-row update, `OptimisticLockingFailureException`). `ReportController` answers both 202, like a deleted page, with no alert (the transaction rolled back, and Discord only hears after a commit) and one log line, `Visitor report dropped because the bio page was deleted meanwhile pageId=…`. Only the bio page path catches them, and the optimistic-lock failure only when the page is gone (`existsById`); otherwise it stays a 500.
  - Resolving (`OK`, or `HIDE` with a reason) closes every open review of the page. `@DynamicUpdate` on `BioPageReview` makes an extend write only `reasons` and `system_flagged` and a resolve only its three fields, so a report can't reopen a review an admin just resolved (it adds its line to that resolved row, and Discord may still say "Visitor report on an open bio page review").
  - The three Discord lines are under Discord alerts; the decisions email counts open bio reviews. MCP moderation tools don't cover bio pages.
- **Text signals** (`BioPageTextSignals` over `SuspiciousUrlService`; a hit flags for review, never blocks; each reason starts with where it was found):
  - handle: `findBrandInHandle` gives the link check's verdict per word or hyphen part (an exact brand, or one swapped letter for brands of 6 or more letters) plus any brand of 6 or more letters inside the handle with `-` and `_` removed, except the common words `booking` and `outlook` → `handle imitates <brand>`; lure words as whole words → `handle has a login or verification lure`
  - display name: `findNamedBrand`, an exact brand on the folded look-alike skeleton only (`PayPal` with a Cyrillic `а` flags, `Cooking` and `Finance` don't) → `name imitates <brand>`
  - name, bio and every button title: alphabet mixing and lure words (`name mixes Latin and Cyrillic letters`, `bio has a login or verification lure`, `a button title …` once); bios and titles get no brand check, because they name platforms ("Follow me on Instagram")
  - words split on anything but letters, marks, digits and format characters, which are then dropped, so a joiner inside a word doesn't hide it
- **Admin** (`DefaultAdminBioPageService`): every write locks the page first; an unknown id or a page deleted before the lock → 404 `Bio page not found`.
  - Search: `BioPageSpecification` (handle, display name or owner email, `lower(…) like … escape '\'` with `\`, `%` and `_` escaped), newest first whatever the caller asks, with one `countByPageIds` and one `openPageIds` query per result page.
  - Hide sets the three hidden fields and resolves open reviews as `HIDDEN`, and publishes nothing (no Discord alert). The owner can still edit a hidden page; it stays hidden until an admin unhides it.
  - Rename follows the owner's rules without the rate limit and flags no text.
  - Revoke clears the handle, stores `handle_revoked_reason` and reserves the old handle (`Revoked bio page handle: <reason>`, cut to 200 on whole characters) unless it is already reserved; a racing `409 This alias is already reserved.` is ignored, any other failure rolls the revoke back. The reservation commits on its own connection (`reserve` is `NOT_SUPPORTED`), so if the revoke's own commit failed the reservation would remain for the admin to free. The owner keeps the page and picks a new handle, which clears the revoked reason. The log names the page id and handle, never an email.
- **GDPR**: the export's `bioPage` and account deletion: see Account self-service. Daily views are counts about visitors, so they are not exported.

### Notifications and consent (`notification_channel`, `notification_consent`, `notification_delivery`, `notification_claim` tables and the `url.destination_*` and `email_log` columns, migration `031-notifications.xml`)
Owner rule: nothing optional is sent without consent, and nothing is on by default (no migration, sign-up path or default grants it).
- **Tables** (031, author `khrvacic`, every changeset with a rollback): `notification_channel` (sealed `target_sealed`, `access_token_sealed`, `signing_secret_sealed`; `masked_target` widened to 300 by `031-notification-channel-masked-target` so the longest host fits; failed-day counters and the last delivery; FK to the user with `CASCADE`), `notification_consent` (one row per grant: `channel_id` with `SET NULL`, `channel_label`, `type`, `granted_at`, `source`, `revoked_at`, `revoked_source`), `notification_delivery` (the queue: `uid`, unique `(channel_id, dedupe_key)`, the signed `body` and the `message`, `CASCADE` with the channel), `notification_claim` (`(user_id, claim_key)`, once-only sends), and on `url` `destination_checked_at`, `destination_dead_since`, `destination_fail_streak`, `destination_last_status`; on `email_log` `consent_type` and `user_id`.
- **Types**: `NotificationType` (`DEAD_LINK_EMAIL`, `WEEKLY_SUMMARY_EMAIL`, `EXPIRY_REMINDER_EMAIL` are email; `LINK_DEAD`, `LINK_BACK`, `DAILY_SUMMARY`, `WEEKLY_SUMMARY` are channel events with wire names `link.dead`, `link.back`, `summary.daily`, `summary.weekly`), `ChannelType` (`DISCORD`, `SLACK`, `TELEGRAM`, `NTFY`, `WEBHOOK`), `ConsentSource` (`SETTINGS`, `UNSUBSCRIBE_LINK`, `CHANNEL_REMOVED`), `DeliveryStatus` (`PENDING`, `SENDING`, `SENT`, `GAVE_UP`) for a delivery row, `LastDeliveryStatus` (`SENT`, `FAILED`, stored as the name in `last_delivery_status` and sent as is in `lastDelivery.status`) for a channel's last attempt.
- **Email is a pseudo-channel** with no `notification_channel` row: it carries dead links, the weekly summary and expiry reminders only (no daily summary and no "link works again" by email).
- **Consent rows**: granting inserts a row; revoking sets `revoked_at` and `revoked_source` on the active one; rows are never deleted on revoke. Active means `revoked_at` null. Grant and revoke take the user row lock (`AccountLock`), so two requests can't leave two active rows; a second grant is a no-op. A channel's ticked events are its active rows (`channel_label` = `"{Type label}: {name}"` at grant time, `Discord: Team alerts`); an edit diffs them. Deleting a channel revokes its rows (`CHANNEL_REMOVED`) and then deletes it; the FK sets `channel_id` null and the label keeps the proof.
- **Active accounts only**: optional emails need an active consent row AND an active owner (`EmailConsentReader`); channels the same (both `findEnabledWithEvent` overloads, by event and by event and owners, require `owner.active`, and the drain gives up on an inactive owner's delivery without a failed day). Deactivation never revokes consent, so reactivation restores it.
- **Consent is checked twice**: when recipients are collected and again right before the message leaves (the email send in `DefaultSendingEmailService`, each delivery attempt). Pinned by `deadLinkEmailNeedsConsent`, `weeklyEmailNeedsConsent`, `expiryReminderNeedsConsent`, `deliveryNeedsActiveEventConsent` (all four channel events), `consentedEmailIsNotSentAfterRevoke` and `resendRefusesWithdrawnConsent`. Transactional email needs no consent and is unchanged: verification, password reset, passkey added, account deactivated, link blocked (single and batch) and malware detected.
- **Unsubscribe tokens** (`UnsubscribeTokens`): `base64url("v1." + userId + "." + TYPE) + "." + base64url(HMAC-SHA256(unsubscribe subkey, payload))`, compared with `MessageDigest.isEqual`, email types only, no expiry. The `List-Unsubscribe` header holds the backend URL (RFC 8058 clients POST to it); the visible link in the email goes to the frontend page `{frontendUrl}/unsubscribe?token=...`, which POSTs on its button.
- **Sealing** (`SecretBox`): channel URLs, bot tokens, ntfy tokens and webhook signing secrets are sealed with AES-256-GCM as `"v1:" + base64(iv(12) | ciphertext | tag(16))`, a fresh IV each time, AAD `notification-channel:<userId>` so a value copied to another user's row won't open. `open` fails with `sealed value can't be opened` and never the value. Secrets are never logged, in an exception, `toString()`, an export, an audit row or a delivery row.
- **Masks are not truncation**: responses carry only `maskedTarget`: `scheme://host/••••` + the target's last 4 characters, or `Bot ••••` + the token's last 4 for Telegram (the chat id is not secret and is returned as is). The four bullets are built in Java only. The webhook signing secret is returned exactly once, on create and on New signing secret.
- **Channel times**: `createdAt` and `updatedAt` come from the injected `Clock`, truncated to microseconds: `create` sets both, an edit and New signing secret set `updatedAt`. There is no JPA lifecycle callback, so every first persist must set both (the columns are `NOT NULL`).
- **Channel validation** (`ChannelTargets`): Discord (`discord.com`, `discordapp.com`, `ptb.` and `canary.discord.com`, path `/api/webhooks/`, default port), Slack (`hooks.slack.com`, `/services/`), Telegram (`botToken` `^\d{5,}:[A-Za-z0-9_-]{30,}$`, `chatId` a number or `@channel`; posts to `https://api.telegram.org/bot{token}/sendMessage`), ntfy (a public https URL with a topic path, treated as a secret; optional printable `accessToken` sent as `Authorization: Bearer`), webhook (any public https URL that isn't a known chat host). One trailing dot on the host is dropped before the target is sealed and masked (`ChannelTargets.normalized`), so `https://discord.com./api/webhooks/...` is stored and posted as `discord.com`. Every target is resolved and checked with `PublicAddresses` at save time and again at send time. The exact field texts are the FE contract (`Paste the URL`, `Use an https URL.`, `We couldn't find this address. Check the URL.`, `This address isn't reachable from the internet. Use a public https URL.`, the per-type shapes). The ntfy `accessToken` shape is checked on an edit that leaves the topic empty too; a blank token keeps the stored one. Bean validation caps the lengths, answered by field like the name: `target` 2048 (`URL must be 2048 characters or fewer`), `botToken` and `accessToken` 255, `chatId` 40 (`Bot token must be 255 characters or fewer`, `Access token ...`, `Chat ID must be 40 characters or fewer`).
- **All field errors in one answer**: the create and edit endpoints take the body without `@Valid`; `ChannelTargets.fieldErrors` runs the DTO's bean validation (the `jakarta.validation.Validator`) and the per-type shape checks together and answers every field in one 400 `{field: message}`; a field that already has a bean error skips its shape check (so an over-long URL is never parsed). These checks run first, before the events check (an unknown event is still `{error}`, but only once the fields are valid) and before the settings rate limit, so a field error spends none of the 60 changes an hour. Only a request with no field errors goes on to the rate limit and then `ChannelTargets.addressError`, the DNS lookup of the target (`NOT_FOUND`, `NOT_PUBLIC`), so a bad name never costs a lookup; a well-shaped but unresolvable URL is reported on the submit after the other fields are fixed. On edit, a changed type is still `{error}` `A channel's type can't be changed...`, checked after the field errors.
- **Messages** (`NotificationMessages`): one `NotificationMessage` per event, rendered per type: Discord as `DiscordMessage.withoutMentionsOrEmbeds` with `DiscordText.plain`, Slack `{"text"}` with `ChatText.slackEscaped`, Telegram plain text (no `parse_mode`, link previews off), ntfy a plain body with `Title`, `Click` and `Tags`, webhook the signed JSON below. At most 20 links, then `and N more`, and within 1,900 characters (whole lines dropped from the end, never cut inside one; a section heading left without its lines goes too, and `and N more` counts links, not headings). They carry counts, short links, destination hosts and dates only: never an IP, User-Agent, referrer, visitor hash or the owner's email. Log lines name ids and the channel type only.
- **Webhooks**: `POST` JSON with `X-Hrva-Event` (the wire name, or `test`), `X-Hrva-Delivery` (the delivery `uid`, the same on every retry) and `X-Hrva-Signature: sha256=<lowercase hex HMAC-SHA256 of the raw body, keyed with the signing secret's UTF-8 bytes>`. Receivers must compare the signature in constant time: Java `MessageDigest.isEqual`, Python `hmac.compare_digest`, Node `crypto.timingSafeEqual` (check the lengths first). Bodies start with `event`, `deliveryId`, `createdAt` (UTC instant of the delivery), then the event's fields (`links`; `date` and `totals` for the daily summary; `from`, `to`, `totals`, `topLinks`, `deadLinks`, `endingSoon` for the weekly one).
- **Delivery queue** (`DefaultNotificationDeliveryService`): an event becomes one row per enabled channel with active consent; the unique `(channel_id, dedupe_key)` makes a re-run a no-op (`link.dead:{night}`, `link.back:{night}`, `summary.daily:{date}`, `summary.weekly:{monday}`), each insert in its own transaction. The drain claims up to 20 due `PENDING` rows (`SENDING`, `claimed_at`), and before each attempt re-reads the channel (enabled, active owner) and the event's consent; gone means `GAVE_UP` with `Not sent: the channel is off or no longer gets this event.`, never a failure. At most 4 attempts: now, then 1, 10 and 60 minutes later, retrying on no connection, a timeout, 408, 429 and 5xx; any other answer and any 3xx give up at once. Rows still `SENDING` after 10 minutes go back to `PENDING`. Every finished attempt sets the channel's `last_delivery_*`; Send test does too, but never touches the failed days.
- **Auto-disable**: a delivery that gives up counts a failed day when `last_failed_day` isn't today (in `app.analytics.zone`); any success resets the count. At 10 the channel turns itself off (`enabled = false`, `auto_disabled_at`), logged by id; the user turns it back on with the switch.
- **Destination check** (`DefaultDestinationCheckService`, 02:00): active links (`active`, no `block_reason`, no `threat_type`) not checked since tonight began, never-checked first, in batches of 200 until none are left or the budget ends; 4 probes at a time on a per-run pool, `HostPacer` keeping 5 s between requests to one host (redirect hops and the GET fallback count against their own host). `PublicHttpFetcher.probe` (User-Agent `hrva.cc-linkcheck/1.0 (+https://app.hrva.cc/help/notifications#link-checker)`): DNS first (`UnknownHostException` is `DEAD nxdomain`, a non-public address `UNKNOWN private`), HEAD then a ranged GET when the HEAD answers 404, 405, 410 or 501, up to 5 hops; 2xx or 304 `ALIVE`, 404 and 410 `DEAD`, every other code (401, 403, 429, 5xx) `UNKNOWN http-{code}`; a refused connection `DEAD refused` (on JDK 25 a refused port arrives as `ConnectException -> ConnectException -> ClosedChannelException`, the same on macOS and Linux), TLS failures `DEAD tls`, a timeout `UNKNOWN timeout`, an unreachable network or host `UNKNOWN unreachable`. `ALIVE` clears the streak and `dead_since`; `DEAD` adds one to the streak and sets `dead_since` when it reaches 3 (three different nights, an unknown or skipped night leaving the streak as it was); `UNKNOWN` only touches `destination_checked_at`. Writes are one JDBC update guarded by the checked `long_url` (`DestinationCheckRepository`), so a result for a destination edited mid-check is dropped; JPA maps the four columns read-only and a destination edit resets them. Before recording a `DEAD` `nxdomain`, `refused` or `tls`, `NetworkCanary` checks that `example.com` or `www.iana.org` resolves; when neither does, the run stops (`Destination check stopped: the network looks down`). It logs `Destination check finished checked= alive= dead= unknown= newlyDead= recovered= stoppedEarly=`, never a URL. Anonymous links are checked and shown to the admin only.
- **Dead-link notices** (`DefaultDeadLinkNotificationService.notify`, after each night): newly dead account links grouped by owner; owners with `DEAD_LINK_EMAIL` get one email, channels with `LINK_DEAD` one delivery; recovered links go to `LINK_BACK` channels only. `dead_since` is set once per dead period, so a link that recovers and dies again may notify again. A newly dead link is notified only while it still exists, is active and still has `destination_dead_since` (a destination edited since the check resets it); a recovered one only needs to exist. The id lists are read in chunks of 1,000. Before `runNightly` hands the outcome over, it adds the account links whose `destination_dead_since` is at or after tonight's start (midnight in `app.analytics.zone`) and that the run didn't report (`DestinationCheckRepository.findDiedSince`), so a run that starts again the same night after a restart still notifies the links the lost run marked dead; a failed read logs one warn line and hands over the run's own outcome. The email claims `dead-email:{night}` in `notification_claim` before each owner's email, so a second notice the same night sends no second email (a lost claim means no email), and the channels are idempotent through `link.dead:{night}`. The same catch-up runs once after every start (`catchUpAfterStartup`, on `ApplicationReadyEvent`, `@Async` on `notificationTaskExecutor` so startup never waits): for the night the next run would use (`analyticsDays.today()`), it reads `findDiedSince` and hands the links to `notify` without probing anything, so a restart in the middle of a run still notifies the links that run marked dead, and a start at noon after a normal night sends nothing new (the claim and the channel dedupe). It is skipped when the check is turned off or `catch-up-on-startup` is false (no SQL), and when a run holds the run flag in this JVM (`Destination check startup catch-up skipped: a run is still going`); while the catch-up holds the flag, a cron firing in that moment is skipped as an overlap and its links are checked the next night. Only account links that are still active count, in the catch-up (`findDiedSince`) and in `notify` (`findActiveStillDeadIds`), the same rule as the dashboard badge and the weekly email's dead list, so a link deactivated after it died gets no email and no `link.dead`. Known limit: `link.back` stays in memory, because `ALIVE` clears the dead columns and no column shows that a link recovered tonight, so a recovery lost to a restart is never sent.
- **Daily summary** (channels only, 01:15): yesterday's totals and the top 20 links by clicks, then bot clicks, then id (bot-only links included); a day with no clicks and no bot clicks sends nothing.
- **Weekly summary** (email and channels, Monday 09:00, the week `DigestWeek.lastClosedBefore(today)`): clicks against the week before, summed daily unique visitors, the top 5 links, links that died this week and are still dead, links ending soon (expiry within 7 days, or at most 10% of the visit limit left, rounded up, and at least 1), each list at most 20 with `and N more` after it (the exact count, in the email's HTML and plain part and in the chat message); nothing when there are no clicks and both lists are empty. The email claims `weekly-email:{monday}` in `notification_claim` first, so a lost claim misses a week rather than doubling it.
- **Account data** (`NotificationAccountData`): the export and the deletion (see Account self-service).
- **Known limit, DNS rebinding**: the public-address check resolves DNS and `HttpClient` resolves again, so a host that changes its answer in between isn't caught (the same as the link previews). Pinning the connection to the checked address needs a custom socket layer and is out of scope in v1.

### Custom domains (`custom_domain`, `custom_domain_allowance`, `custom_domain_reconcile`, `custom_domain_cap_lock` tables and `url.domain_id`, migration `032-custom-domains.xml`)
A signed-in user applies for a subdomain they own (`go.example.com`); an admin approves or rejects it. Approval creates a Cloudflare for SaaS custom hostname on the hrva.cc zone (fallback origin `domains.hrva.cc`), the user adds one CNAME to `domains.hrva.cc`, and the lifecycle job polls Cloudflare until the hostname and its certificate are active. Links on the domain (`go.example.com/menu`) have their own alias namespace. No hostname is ever created without an approved application. Code: `service/domain/`, `DefaultCustomDomainService` (the owner), `DefaultCustomDomainAdminService` (admin), `client/CloudflareClient`, `security/CustomHostFilter`, the controllers `CustomDomainController` and `AdminCustomDomainController`. Endpoints: see Key Endpoints. The FE builds against the same JSON (`lib/types.ts` in URL-Shortener-FE).
- **Tables (032, author `khrvacic`, eight changesets, each with a rollback)**:
  - `custom_domain`: `owner_id` (FK `fk_custom_domain_owner` to `user_account`, `SET NULL`), `hostname`, `hostname_key` (unique `ux_custom_domain_hostname_key`; null once nothing holds the hostname), `status`, `reason` (≤ 300), `apply_flags`, `review_note` (≤ 500), `reviewed_by`, `reviewed_at`, `cloudflare_id`, `cloudflare_status`, `cloudflare_ssl_status`, `last_error` (admin only, ≤ 500), `problem`, `next_check_at`, `last_checked_at`, `check_count`, `activated_at`, `disabled_reason`, `disabled_note`, `disabled_at`, `deleted_at`, `cloudflare_delete_pending`, `created_at`, `updated_at`; indexes on the owner, `(status, next_check_at)` and the delete flag. `CustomDomain` is `@DynamicUpdate` and `@BatchSize(50)`; rows the lifecycle job writes change only through status-guarded `@Modifying` updates (`… where id = :id and status = :expected`, flushing and clearing the persistence context, so re-read after one) or JDBC, never by saving a copy.
  - `custom_domain_allowance(user_id, max_domains, reason, granted_by, granted_at)`, cascade from the user.
  - `custom_domain_reconcile(id, ran_at, cloudflare_total, ours_in_cloudflare, unknown_hostnames, missing_domain_ids, error)`: one row per reconcile, kept 30 days; `missing_domain_ids` holds `id:hostname` lines.
  - `custom_domain_cap_lock`: one row (`id = 1`), locked `for update` by every approval and setup.
  - **Lock order** (a rule for new code, so no two paths wait on each other in a cycle): user row, then `custom_domain_cap_lock`, then domain rows. Approval and setup take the cap lock, then the row; blocking a user and account deletion take the user row, then the domain rows; link creation takes the domain row alone (`select status … for update`).
  - `url.domain_id` (FK `fk_url_custom_domain`, no cascade; `idx_url_domain_id`) and the unique `ux_url_domain_short_url (domain_id, short_url)` **NULLS NOT DISTINCT**, which replaces `UX_URL_SHORT_URL` (see Unique short URLs).
- **Statuses** (`CustomDomainStatus`, stored by name): `PENDING_REVIEW` → `APPROVED_PROVISIONING` → `AWAITING_DNS` → `ACTIVE`, plus `REJECTED`, `DISABLED`, `ERROR`, `DELETED`. Every status but `REJECTED` and `DELETED` holds the hostname (a `DELETED` row keeps it only while its Cloudflare delete is queued); `PENDING_REVIEW`, `APPROVED_PROVISIONING`, `AWAITING_DNS`, `ACTIVE`, `DISABLED` and `ERROR` count toward the user's limit. `DomainDisableReason`: `ADMIN`, `USER_BLOCKED`, `DOMAIN_RULE`, `BLOCKLIST`. `DomainProblem` and its user text (`DomainProblems.text`): `DNS_NOT_FOUND` `We can't see the CNAME record yet. DNS changes can take up to an hour.` (only from 10 minutes after approval), `CAA_BLOCKED`, `CERTIFICATE_TIMED_OUT`, `CNAME_REMOVED`, `CLOUDFLARE_BLOCKED`, `PROVISIONING_FAILED` `Something went wrong setting up your domain. We've been told and will look into it.` (the FE card shows its own text with a Retry button instead: one while the automatic retries run, one once they stopped), `DNS_TIMED_OUT` `We waited 14 days and never saw the CNAME record, so we stopped checking. Add the record, then select Check now.` A stopped `ERROR` row (`PROVISIONING_FAILED`, `DNS_TIMED_OUT`) is never due; it waits for Check now or Retry.
- **Cloudflare's quota isn't the billing boundary.** `GET /custom_hostnames/quota` answers `allocated: 50000`, and the API will create a 101st hostname. The 100 free hostnames and the $0.10 per hostname per month after them are billing-side and can't be read with the token. The app's cap and the free-allowance check are the only guards, and every hostname that exists or is about to exist in Cloudflare counts, whatever its status: **slots in use** = rows `APPROVED_PROVISIONING`, or with a `cloudflare_id` and (not `DELETED`, or a delete queued).
- **Status mapping** (`CloudflareStatusMapping`, pure; `steps.dnsFound` = hostname `status` `active`, `steps.certificateIssued` = `ssl.status` `active`):

  | Cloudflare hostname `status` | `ssl.status` | Our status | `problem` |
  |---|---|---|---|
  | `active` | `active` | `ACTIVE` (sets `activated_at` the first time) | null |
  | `active` | anything else not timed out | `AWAITING_DNS`; an `ACTIVE` row stays `ACTIVE` (certificate renewal) | `CAA_BLOCKED` when a validation error mentions CAA, else null |
  | `pending`, `pending_provisioned`, `provisioned`, `active_redeploying`, `test_*` | not timed out | `AWAITING_DNS`; an `ACTIVE` row stays `ACTIVE` | `DNS_NOT_FOUND` after 10 minutes, `CAA_BLOCKED` as above |
  | any | `*_timed_out`, `expired` | `ERROR`; an `ACTIVE` row stays `ACTIVE` with the certificate state in `last_error` | `CERTIFICATE_TIMED_OUT` (or `CAA_BLOCKED`) |
  | `moved`, `deleted`, `pending_deletion` on a row that was active | any | `ERROR` | `CNAME_REMOVED` (and a Discord alert) |
  | `moved` before it was ever active | any | `AWAITING_DNS` | `DNS_NOT_FOUND` |
  | `blocked`, `pending_blocked` | any | `ERROR` | `CLOUDFLARE_BLOCKED` (and a Discord alert) |
  | gone from Cloudflare (404) on a row that isn't deleted | — | `ERROR` | `PROVISIONING_FAILED`, `last_error` `Cloudflare no longer has this hostname` |

  An `ACTIVE` domain leaves `ACTIVE` only for hostname-level failures (CNAME gone, blocked, moved, missing in Cloudflare), never for its certificate alone; an `ERROR` row that was once active waits for an active certificate before it returns to `ACTIVE`. `last_error` is the first of `verification_errors[0]`, `ssl.validation_errors[0].message` or the API's `errors[0].message`, cut at 500.
- **Rulings, as built** (the plan's 25, with the decisions made while building):
  1. `domain_id` null means hrva.cc; `NULLS NOT DISTINCT` keeps two hrva.cc links from sharing an alias (nulls are distinct by default on both databases). It needs Postgres 15: `032-url-postgres-15` (Postgres only) halts startup below 15 before anything half-migrates.
  2. `ShortUrlUniqueIndex.violatedBy` matches `UX_URL_DOMAIN_SHORT_URL`; `enforced()` is true when `032-url-domain-short-url-unique` is `EXECUTED`, false when it is `MARK_RAN` (duplicates per domain; the startup warning stays), and without that row the 027/030 rule decides. `Url.shortUrl` lost `unique = true`; the Hibernate test schemas get the composite constraint.
  3. `Url.domain` is an eager `@ManyToOne` (`@JoinColumn(name = "domain_id")`), so a `UrlResponse` built after its transaction still has the hostname. A link's domain is fixed at creation (no edit, admins included); moves are targeted JDBC (`UrlDomainMoves`).
  4. One cache key shape (`UrlCacheKeys.of(domainId, alias)`), see Cache Architecture.
  5. **Hostnames** (`CustomDomainHostnames.normalize`): trim, lower-case (`Locale.ROOT`), strip one trailing dot, IDN to punycode (a Cyrillic look-alike shows as `xn--`; labels are checked against an RFC 3492 decode and re-encode and an IDNA2008-style code point allowlist, non-NFC labels and a leading combining mark refused). Refused with 400 on `hostname`: blank `Enter a domain, like go.example.com`; over 253 `A domain can be 253 characters at most.`; bad shape (characters, an empty label, a label over 63, a leading or trailing hyphen, `*`, `_`) `Enter a domain like go.example.com: letters, digits and hyphens, with dots between the parts.`; emoji or symbols `Emoji and symbol domains can't be used. Use a domain made of letters and digits.`; an apex (the hostname is its own registrable domain, so `example.co.uk` too) `Use a subdomain, like go.example.com. Root domains like example.com aren't supported yet.`; an IP literal, `localhost` or `*.localhost`, a public suffix or no registrable domain `Enter a domain you own, like go.example.com.`; `app.domains.reserved` or a subdomain of one, or a link check `BLOCK` `This domain can't be used on hrva.cc.` A hostname already held → 409 `This domain has already been applied for.` (also on a lost race on `ux_custom_domain_hostname_key`). Applications whose labels start with `xn--` get the apply flag `International name (punycode): check it doesn't imitate another domain`.
  6. **Approval**: a cheap read first (404, 409 `This application was already reviewed.`, or 409 `This domain matches a block rule.` from `LinkCheckService.isBlockedByRule`, all without asking Cloudflare), then the token check and a live probe (`GET /custom_hostnames?per_page=5`, its `total_count`), then one write transaction: the cap-lock row `for update`, the row re-read, status `PENDING_REVIEW`, owner active, token `OK`, slots in use < `max-active`, and the live total plus the rows still `APPROVED_PROVISIONING` < `free-allowance`. A probe that fails refuses the approval (the allowance can't be proven). It writes `APPROVED_PROVISIONING`, `reviewed_*` and `next_check_at = now`; the setup starts after the commit.
  7. **Setup** (`CustomDomainProvisioner.provision`, the only caller of `CloudflareClient.create`, pinned by `CloudflareCreateCallersTest`): it re-reads the row and goes on only for `APPROVED_PROVISIONING` with `reviewed_at`; looks the hostname up (`?hostname=`) and adopts an existing one (a lost create response, or a hostname the owner added by hand); probes the live total again right before the create and refuses at total plus in-flight ≥ the free allowance (`Cloudflare's free allowance is full`, a failed attempt); then `POST {"hostname", "ssl": {"method": "http", "type": "dv"}}` and nothing else (no `custom_metadata`). A duplicate answer (409 or code 1406) is followed by one more lookup. Failed attempts retry after 1, 5 and 30 minutes, then hourly for 24 hours, then wait for Retry; each failure shows `PROVISIONING_FAILED` at once. A row removed meanwhile gets its new hostname deleted again; one turned off meanwhile keeps it. An adopted hostname whose domain vanished stays in Cloudflare and shows as drift.
  8. **No HTTP inside a transaction, deletes queued**: every Cloudflare call runs outside a transaction (and with no connection held), and its result is written with a status-guarded update. Removals and account deletion mark the row `DELETED` with `deleted_at` and `cloudflare_delete_pending` when it has a `cloudflare_id` (else `hostname_key` null at once); the lifecycle job calls `DELETE` (404 counts as done) and clears the flag and `hostname_key`. A restart catches up by itself, since rows are due by `next_check_at` or the flag.
  9. **Hosts** (`HostRouting.classify(request.getServerName())`, ahead of `ForwardedHeaderFilter`): primary (the host of `app.server-url` and `app.domains.primary-hosts`), custom (in the registry as `ACTIVE` or `DISABLED`) or unknown (404). See Security.
  10. **The root of a custom domain** → `302 {frontendUrl}/` with the no-store headers: the same target as the primary host's 301, but never cacheable, so a per-domain home page can come later.
  11. **`CustomDomainRegistry`** holds `hostname → DomainRoute(id, hostname, status, ownerActive)` for `ACTIVE` and `DISABLED` rows in memory. It loads once every bean exists (before the server takes requests), every 60 s (`reloadCustomDomainRoutes`), after the commit of any domain write (`CustomDomainChangedEvent`), and after an account is deactivated or reactivated (`AccountActiveChangedEvent`, from `DefaultUserService`), so an owner's domain stops or starts serving at once; a failed reload keeps the previous routes, and any other change is seen within a minute. **This assumes the single container**: a second instance would see another's writes only on its next 60 s reload, and the lifecycle's `AtomicBoolean` overlap guard, the in-memory token state and the reconcile quota are per JVM.
  12. **The domain sits in front of the link cache**: on a custom host the route is checked first, so a `DISABLED` domain answers `302 {frontendUrl}/unavailable?s={alias}&reason=domain&d={hostname}` and a deactivated owner's `…&reason=inactive&d={hostname}` before the `urls` cache is read. Other redirects from a custom host: an unavailable link → `…/unavailable?s={alias}&reason={reason}&d={hostname}`, a password link → `{frontendUrl}/protected/{alias}?domain={hostname}`.
  13. Reserved aliases are global (refused on every domain, and a built-in one answers 404 on a custom host); random aliases are drawn per domain; uniqueness, the lost-race 409 and reactivation are per domain.
  14. **Links on a domain**: the caller is signed in (web, API key or the signed-in MCP user), owns an `ACTIVE` domain with that hostname and is active; admins get no exception. The domain row is read `for update` (status only) while the link is inserted, so a create can't land on a domain being removed. Reactivating a link whose domain isn't `ACTIVE` → 400 `This link's domain isn't active, so the link can't be turned on.` Everything else on a link (limits, passwords, expiry, analytics, every check, the review queue) runs by link id as before.
  15. **Removal** (`CustomDomainRemoval.remove`, shared by the owner and the admin): `DEACTIVATE` (default) turns every active link off in one update and keeps `domain_id`, so the links still show their host; `MOVE` sets `domain_id` null link by link, keeping the alias when it is free on hrva.cc and not reserved, else a random one (a lost race retries once), and lists the renames. Every affected cache key is evicted, old and new. Only an admin's removal emails the owner, and not for a row already `REJECTED`.
  16. **Turn off and on**: off keeps the domain, its links and its Cloudflare hostname (it still uses a slot), stops serving at once and stops polling, records `disabled_*`, alerts Discord and emails the owner. On sets `AWAITING_DNS` and checks at once; a domain turned off before it had a `cloudflare_id` becomes `ERROR`/`PROVISIONING_FAILED` (`It was turned on again before setup finished.`) and waits for Retry, which passes the full gate.
  17. **Abuse**: applying runs the link check on `https://{hostname}/` (`BLOCK` refused with the reserved text, `FLAG` stored in `apply_flags`). A new Block rule (or Block domain) turns off every domain that is the rule's domain or under it, unless a more specific Allow rule covers it (`DOMAIN_RULE`, note `ruleDomain: reason`), counted in `domainsDisabled`; removing the rule turns nothing back on; `PENDING_REVIEW` rows aren't touched (approval refuses them). Block user turns off the user's domains (`USER_BLOCKED`) and rejects their applications (`Account blocked`, no email); unblock turns on only `USER_BLOCKED` ones. The 03:40 job runs the link check over every `ACTIVE` hostname and turns off a `BLOCK` (`DOMAIN_RULE`, else `BLOCKLIST`). A moderation restore of a link keeps it off only when its domain is `DELETED`; otherwise it is turned on and the route keeps it unserved while the domain is off. Reports take `go.example.com/menu` for a domain that is `ACTIVE` or `DISABLED`.
  18. **Alerts** (`AdminAlertEvent`): `DomainApplied` (`New custom domain application: go.example.com (flags), account #5, <link>`), `DomainDisabled`, `DomainNeedsAttention` (setup failed, Cloudflare blocked, CNAME removed) and `DomainDrift`, each linking to `{frontendUrl}/admin/domains?search={hostname}&id={id}`; hostnames go through `DiscordText.hostname` (escaped, never IP-scrubbed). A missing hostname alerts on its first night only (a hostname already in the previous completed run's missing list is known; a failed run doesn't count as a night in between), and a row the lifecycle marked gone also appears once in that night's drift line. The FE review badge adds `PENDING_REVIEW` applications.
  19. **Account data** (`CustomDomainAccountData`): the export's `domains` (last) lists every row the user owns, every status, newest first: `hostname, status, reason, reviewNote, createdAt, reviewedAt, activatedAt, disabledAt, deletedAt, disabledReason, disabledNote` (the user-facing turn-off text), never Cloudflare ids, `last_error`, `apply_flags` or `reviewed_by`. Deletion: `releaseFor(user)` (under the account lock, before `urlRepository.deleteByOwner`) deletes `PENDING_REVIEW` and `REJECTED` rows without a `cloudflare_id`, marks the rest `DELETED` with the owner cleared and the Cloudflare delete queued, clears `reason`, `review_note`, `reviewed_by`, `apply_flags` and `disabled_note`, and removes the account's hostnames from stored reconcile runs; `purgeFor(ids)` after the links deletes the rows with nothing queued, and the lifecycle deletes an owner-less row once its Cloudflare delete succeeds. Deactivation changes nothing (the active-owner rule: the domain stops serving with `reason=inactive` and takes no new links until reactivation).
  20. **Emails** (transactional, through `tryToSendEmail`: no consent, no unsubscribe footer; always after the commit, wrapped so a failed send never undoes the change): `domain_approved` `Your domain {hostname} is approved: one step left` (the CNAME record), `domain_rejected` `Your domain application for {hostname}` (the note), `domain_disabled` `Your domain {hostname} was turned off` (the reason text, for every reason), `domain_removed` `Your domain {hostname} was removed` (admin removals only, with the moved, renamed and turned-off links). No "your domain is ready" email.
  21. **Short links outside the app** carry their host through `ShortLinks` (`url`, `display`, `host`, `hostnameOf`): notification messages and webhook payloads (`shortUrl` points at the custom host; no separate `domain` field), the blocked-link, expiry, decisions, malware, dead-link and weekly emails, Discord alerts and the digest, MCP answers, the owner's CSV and `/qr`.
  22. **MCP**: every tool prints the right host, and `link_stats` takes `go.example.com/menu` for the caller's own link (a bare alias matching several links prefers active, then hrva.cc). `shorten_url` has no `domain` parameter.
  23. **Token check** (`CloudflareTokenCheck`): at startup (`@Async`, fail-soft), on demand, before every approval and setup retry, and at the start of each reconcile; kept in memory, never the token. Blank token or zone → `MISSING` (`CLOUDFLARE_API_TOKEN or CLOUDFLARE_ZONE_ID isn't set.`) with no HTTP call. `GET /user/tokens/verify` (user tokens only; an account token is judged by the probe), then the probe: 200 → `OK`; 401 → `INVALID` `Cloudflare doesn't accept the token.`; 403 after an active verify → `NO_PERMISSION` `The token works but can't read custom hostnames on this zone.`; 403 otherwise → `INVALID` `Cloudflare refused the token. Check that it's valid and has SSL and Certificates edit permission on the hrva.cc zone.` (Cloudflare can't tell a bad token from a missing permission); a timeout, connection failure or 5xx → `UNREACHABLE` `Cloudflare couldn't be reached. We'll check again.` Before the first check `checkedAt` is null (the FE shows "Not checked yet").
  24. **Reconcile** (`CustomDomainReconciler`): lists every Cloudflare hostname (`per_page=50`, every page, one more after a full last page), compares it with our rows holding a `cloudflare_id`, re-asks for a hostname the listing skipped before marking it, and records the run, the quota and the total. Unknown in Cloudflare and not in `ignored-hostnames` → drift; ours (not `DELETED`) missing → drift and `ERROR`/`PROVISIONING_FAILED`. It never deletes anything, ignored hostnames included. Runs older than 30 days are deleted.
  25. **The lifecycle job** (`CustomDomainLifecycle.runInBackground`, `@Async` on `notificationTaskExecutor`, `NOT_SUPPORTED`, an `AtomicBoolean` skipping an overlapping run): sets up due `APPROVED_PROVISIONING` rows, checks due `AWAITING_DNS`, `ACTIVE` and re-checkable `ERROR` rows, and runs queued deletes, each row in its own short transactions, `next_check_at nulls first, id`, one count line per run: at most 50 setups, 50 checks shared across `AWAITING_DNS`, `ACTIVE` and `ERROR` in that order, and 50 deletes. Schedule: `AWAITING_DNS` every minute for the first hour after approval, every 10 minutes until 24 hours, then hourly; after 14 days without the CNAME ever seen, `ERROR`/`DNS_TIMED_OUT` and no more checks; `ACTIVE` daily (it notices a removed CNAME); re-checkable `ERROR` hourly.
- **Redis keys** (through `RateLimiter.tryAcquire`): `rate-limit:domain-apply:user:<id>`, 5 applications per 24 hours, taken only after the hostname and the user's limit are checked (so a typo or an application at the limit costs nothing; a taken hostname still costs one, so the 409 can't be used to probe for applications for free), fail-open with one warn line (a person reviews every application); `rate-limit:domain-check:domain:<id>`, the live check behind `GET /users/me/domains/{id}`, 1 per 15 s, fail-closed (with Redis down the stored status is served and Cloudflare isn't called); `rate-limit:domain-retry:domain:<id>`, the owner's Retry, 1 per 15 s (429 `Wait a few seconds and try again.`; with Redis down the retry goes ahead, the approval gate still applies).
- **The fake Cloudflare** (`scripts/mcp-e2e/fake-cloudflare.py`, Python 3 standard library, state in memory): the subset of the API the client uses (token verify, list with `hostname`/`page`/`per_page` (5 to 1000), create, quota, get, delete) with Cloudflare's error codes (409/1406 duplicate, 404/1436, 400/1432 and 1433, 403/1413 `custom_metadata`), and control endpoints that are never logged as calls: `POST /_control/activate?hostname=`, `/_control/state?hostname=&status=&ssl=&error=`, `/_control/token?mode=ok|account|invalid|forbidden|down`, `/_control/reset[?scope=calls]`, `GET /_control/calls` and `/_control/hostnames`. Start it with `python3 scripts/mcp-e2e/fake-cloudflare.py --port <port>` and pass `--app.cloudflare.api-base=http://127.0.0.1:<port>/client/v4 --app.cloudflare.api-token=<anything> --app.cloudflare.zone-id=<anything>`. Tests use the in-process `service/domain/FakeCloudflare` instead. Never use the production token locally or in a test.

## Cache Architecture
- **Cache name**: `urls`
- **Keys** (`UrlCacheKeys.of(domainId, alias)`): the alias for a hrva.cc link (the keys from before custom domains stay valid) and `<domainId>/<alias>` for a link on a custom domain (`/` can't appear in an alias). Every read, write and evict uses it: `DefaultUrlService`, the three `@CacheEvict(key = "#result.cacheKey()")` (`UrlResponse.cacheKey()`, `@JsonIgnore`), the visit-limit evict in `DefaultClickAnalyticsService.recordClick(urlId, cacheKey, click)`, `DefaultModerationService`, `CacheWarmup` and the `unlock:<cacheKey>` rate-limit keys. A domain removal evicts every key of its links, old and new.
- **TTL**: 1 hour (configurable in `AppCacheConfiguration`), which bounds how long a stale entry can outlive a missed eviction, as a cached hit never rereads the block fields
- **Used by**: `redirectResultUrl` (redirect) and `peekUrlByShortUrl` (peek) — both use manual `CacheManager` access
- **Validation on cache hit**: `isUrlRedirectValid()` checks active, expirationDate, visitLimit/visits before serving
- **Eviction**: `@CacheEvict` on revokeUrl, activateUrl, updateUrl (by key), deleteUrl (all entries). A moderation block or reactivation evicts once it commits and again 2 s later on the scheduler (`TaskScheduler`, fail-soft), so a click that read the row just before the commit can't leave the old answer cached
- **Warmup**: `CacheWarmup` loads top 20 most visited, most recent, and recently accessed URLs on startup
- **Priming**: New URLs cached immediately on creation via `cacheUrlResponse()`
- **Graceful degradation**: `CacheErrorHandler` logs and falls through to DB on Redis failure
- **Statistics**: on (`spring.cache.cache-names: urls` and `spring.cache.redis.enable-statistics: true` in `application.yaml`; Boot builds the `RedisCacheManager`, the app declares only its `RedisCacheConfiguration`). `RedisCache.getStatistics()` counts hits and misses in memory since the last restart, for the link cache hit ratio on the System tab and the Health page (see Admin stats).

## Click analytics
Daily per-link counts with no raw IP, full User-Agent, full Referer or salt ever stored in Postgres, logged, put in a metric or returned.
- **A click** is a request that sends someone on to the destination: the redirect `/{short}` (from the database or a cache hit), `GET /api/v1/urls/{short}` for a link without a password, and a successful `/unlock`. `/peek`, `/preview`, `/qr` and the admin views are not clicks, and a click the click check refuses (`reason=blocked`) records nothing. A password-protected link's `GET /urls/{short}` records nothing; its click is the unlock.
- **Recording**: the controllers build a `ClickRequest` with `ClickRequestResolver` (the IP from `ClientIpResolver`, `User-Agent`, `Referer`, a single `CF-IPCountry`, and `qrScan`; `toString()` redacts), and `DefaultUrlService` hands it to `ClickAnalyticsService.recordClick(urlId, shortUrl, click)`. The recorder takes the day on the request thread and does the rest on `applicationTaskExecutor`, which finishes its queue on shutdown (see Executors). It never throws; each write is fail-soft and a failure logs the link id, the step and the exception class only.
- **Derived and stored** (the full User-Agent and Referer are dropped after classification):
  - day, and bot or human
  - referrer: the host lowercased without `www.`, `direct` (no header), `unknown` (unlock), `app:<package>` (`android-app://`), the configured server host (hrva.cc in production; `ReferrerClassifier.ownHost()`) for the server and frontend hosts, `other` (unparsable, or a host without a dot such as `localhost`)
  - country: from `CF-IPCountry` only, never from the IP: ISO alpha-2 upper case, `unknown` (missing or `XX`), `tor` (`T1`)
  - device `mobile`, `tablet`, `desktop`, `unknown`; browser `chrome`, `safari`, `firefox`, `edge`, `samsung`, `opera`, `in-app`, `other`; os `ios`, `android`, `windows`, `macos`, `linux`, `chromeos`, `other`
  - source: `qr` for a QR scan, otherwise `direct`
- **QR scans**: every hrva.cc QR code (`/api/v1/urls/{short}/qr` and the frontend's QR codes) encodes `<short link>?qr`. `ClickRequestResolver` marks a click as a QR scan (`ClickRequest.qrScan`, `withQrScan()`; `withUnknownReferrer()` keeps it) when the request has a parameter named exactly `qr` (`QR_MARKER`), with any value or none: `?qr`, `?qr=`, `?qr=1` and `?fbclid=abc&qr` are scans, while `?QR`, `?qrcode=1`, `?utm_source=qr` and no query are direct. A query the server can't parse (Tomcat 11's `getParameter` throws an `IllegalStateException` on `%zz`, `=x` or `a=%`) counts as direct, even with `qr` in it, so a link such as `hrva.cc/abc?utm_campaign=50%off` still redirects instead of failing with a 500. The redirect never passes the request's query on (`RedirectView`'s `propagateQueryParams` stays off, pinned for all four views in `UrlServiceTest.noRedirectPassesTheVisitorsQueryOn`), so the destination never sees `qr` or any visitor parameter, and a destination's own `?qr=keep` survives. A password-protected link's scan counts as direct, because its click is the frontend's `/unlock` call, which carries no `qr`. Clicks recorded before v2.11 have no `SOURCE` row, so the frontend shows Direct as clicks − QR scans, never the stored `direct` count.
- **Counting rules**:
  - A bot (`UserAgentClassifier`: a blank User-Agent, a named bot, link-preview fetcher or HTTP library (among them Outlook desktop's `Microsoft Office/` probe, which fetches a clicked link before it opens the browser), or the generic `bot`, `crawler`, `spider`, `preview` once the phone brand `cubot` is removed) adds one `BOT_CLICKS` and nothing else: no breakdowns, no unique visitor, no `Url.visits`, no `lastAccessed`.
  - On a visit-limited link (`visitLimit > 0`) a bot never gets the destination: the redirect (database or cache hit) goes to `reason=missing`, `GET /urls/{short}` and `/unlock` answer 404 `URL doesn't exist`. The request is still recorded, as a bot click. The check runs on the request thread: on the redirect and `/unlock` it runs before the click check, on `GET /urls/{short}` the click check runs first. A classifier failure counts as human. Links without a limit redirect bots as before.
  - A human click adds one `CLICKS` and one breakdown row per dimension, six in all. Unlock clicks record the referrer as `unknown`, since the unlock comes from the frontend.
- **Unique visitors** (`UniqueVisitorCounter`): `HMAC-SHA256(daySalt, ip + "\n" + userAgent + "\n" + urlId)`, its first 16 bytes as 22 Base64url characters, added to the link's set for the day. A new member adds one `UNIQUE_VISITORS` plus `recordVisit` (`visits` + 1 and `lastAccessed`, active links only) and `deactivateAtVisitLimit`, which evicts the cached entry when it switches the link off. `Url.visits` is therefore daily unique human visitors, summed.
  - `analytics:salt:<yyyy-MM-dd>`: Base64 of 32 `SecureRandom` bytes, created with set-if-absent. `analytics:visitors:<urlId>:<yyyy-MM-dd>`: the set. Both expire at the next midnight in the zone plus 4 hours; every write sets the expiry, so no analytics key lives without one.
  - Redis down, or a failing check → a new visitor, so a visit-limited link closes early rather than late (one warn line, without the IP). A lost salt is recreated and that day over-counts once.
  - Bio page views use the same salt and expiry: `isNewBioPageVisitor` hashes `ip\nua\nbio:<pageId>` into `analytics:bio-visitors:<pageId>:<yyyy-MM-dd>`, so a page hash never equals a link hash. It is appended after line 100 of `UniqueVisitorCounter`; lines 1–100 must stay as they are, because the FE landing page quotes `visitorHash` (lines 58–62) by line number, and `AnalyticsDays` is never edited.
- **Tables** (`026-privacy-first-analytics.xml`, `LinkStatsRepository`, deleted with the link): `LINK_DAILY_STATS(URL_ID, STAT_DATE, CLICKS, UNIQUE_VISITORS, BOT_CLICKS)` and `LINK_DAILY_BREAKDOWN(URL_ID, STAT_DATE, DIMENSION, DIMENSION_VALUE, CLICKS)`, `DIMENSION` one of `REFERRER`, `COUNTRY`, `DEVICE`, `BROWSER`, `OS`, `SOURCE` (`StatDimension`; `SOURCE` came in v2.11 and fits `DIMENSION`'s `VARCHAR(10)`, so it needed no changeset). 026 also drops the old `ip_address` table and its sequence in two changesets, `026-drop-ip-address` and `026-drop-ip-address-seq` (no rollback), each behind a `tableExists` or `sequenceExists` precondition with `onFail="MARK_RAN"`: a database where either is already gone marks that changeset ran instead of failing Liquibase, and with it the startup of the only container. `table/ip_address.xml` stays in the changelog, so a fresh database creates both and 026 drops them.
  - Upserts are standard SQL `MERGE … USING (VALUES …) AS s(…)` with every parameter wrapped in `CAST(:p AS <type>)`, because Postgres can't type bare parameters inside `VALUES`. Never `ON CONFLICT` or H2's `MERGE … KEY`: the same SQL runs on H2 in the tests and on Postgres 15 or newer. A duplicate-key race is retried once.
  - Caps: at most 50 named values per dimension per link per day; a further new value, or one over 255 characters, is stored as `other`. The per-link view shows the top 10 named values per dimension plus one `other` (stored `other` plus the rest), left out when 0.
- **Reads** (`DefaultAnalyticsService`, for `GET /api/v1/analytics/urls/{id}`, MCP `link_stats` and `GET /api/v1/analytics/overview`): `days` 7, 30, 90 or 365 (`AnalyticsRange`, default 30; anything else → 400 `days must be 7, 30, 90 or 365`, which the service checks before it reads the caller or the link). The range ends today in the analytics zone and starts `days − 1` days earlier. `findDaily` returns only the stored days and the service zero-fills the rest, so `daily` always has `days` entries; the totals are their sums. `findBreakdownTotals` sums each value over the range, clicks descending then value ascending; the service keeps the top 10 named values and appends `other` last. `breakdowns.sources` (`qr` and `direct`) is the last breakdown, in the per-link analytics and the admin Traffic tab alike; MCP `link_stats` doesn't print it. The summary has the destination host and, as its last field, the full destination `longUrl`, so the link page can show its campaign (UTM) tags; only the owner or an admin reads it (anyone else gets 403, password-protected links included, and no unauthenticated or peek path returns this summary), and MCP `link_stats` still prints the host only. The overview's top links keep the host only, never the full URL. The overview sums the caller's links per day (`findOwnerDaily`) and lists the top 10 links by clicks in the range (`findOwnerTopLinks`: clicks descending then link id, bot-only links left out), each with the short URL and destination host from the caller's own links; its unique visitors are a sum over links and days, so one person on two links counts twice. `IDX_URL_OWNER_ID` (026) indexes `URL.OWNER_ID` for these owner-scoped reads, as Postgres doesn't index a foreign key column by itself.
- **Day**: `app.analytics.zone` (`APP_ANALYTICS_ZONE`, default `Europe/Zagreb`; the container runs in UTC), taken by `AnalyticsDays` on the request thread when the click arrives. The salt and set expiry follow the same day boundary.
- **Write budget per human click**: one stats `MERGE`, one 6-row breakdown `MERGE` and one read for the cap; a new unique visitor adds `recordVisit` and `deactivateAtVisitLimit`. A bot click is one statement. Counts go straight to Postgres, never buffered in memory (a redeploy would lose them).
- **No IP logging**: click-path log lines name the short code or link id only.
- **Never cache redirects**: every click has to reach the backend through Cloudflare (`cf-cache-status: DYNAMIC`), or analytics silently undercounts.

## Admin stats
Site-wide aggregates for the FE stats page (`/admin/dashboard`), one endpoint per tab (`GET /api/v1/admin/stats/{traffic|links|users|safety|system}`, see Key Endpoints), each loaded on its own. `AdminStatsController` → `DefaultAdminStatsService`, which checks `days` and builds the `StatsWindow` → one collector per tab in `service/stats/` → one JDBC repository per tab in `repository/stats/`.
- **Range**: `days` 7, 30, 90 or 365 (default 30) through `AnalyticsRange.fromDays`, the same check and 400 as the analytics endpoints. The window ends today in `app.analytics.zone` and starts `days − 1` days earlier, and every daily series has exactly `days` entries, zero-filled. The System tab checks `days` too and uses it only for the emails series.
- **Days of stored timestamps** (`StatsDays`): entity timestamps are `LocalDateTime` in the JVM zone (UTC in the container). `window(range)` and `window(from, to)` turn a range or a closed date range into stored-time bounds (`storedStartOf(from)` up to `storedStartOf(to + 1 day)`; the range variant is `window(today − (days − 1), today)`, and `from` after `to` is refused). The closed-range form, with the four `AdminStatsService` overloads `traffic`, `links`, `users` and `safety(from, to)`, is internal: the weekly digest and the public numbers use it, and no endpoint takes dates. `dayOfStored` puts a stored time on its analytics-zone day, and `storedNow()` is the current time in the stored zone. "Now" figures bind `storedNow()` as a parameter (`:now`, `:today`), never the database's `current_timestamp`, so a database session zone can't skew them and a fixed clock can test them.
- **Hour buckets**: links created, sign-ups, reviews opened, blocks and emails are counted per stored date and hour in SQL (`HourlyCountRepository`: `cast(ts as date)`, `extract(hour from ts)` and a key, one `HourlySeries` per chart), and `DailyBuckets` assigns each hour to its analytics-zone day, so these series use the same days as the click series. That relies on the zone's offset being whole hours, as Europe/Zagreb's is. A series lists its known keys first, then any other key that turns up. A key is never null (`DailyBuckets` would throw): a nullable key column is wrapped in `coalesce(…, 'unknown')` (`created_via`, `block_reason`) or `coalesce(auth_provider, 'local')`.
- **Traffic** (`link_daily_stats`, `link_daily_breakdown`, `url`): clicks, unique visitors and bot clicks in range, the daily series, clicks on anonymous and on account links, the top 10 links by clicks (short URL, destination host, owner email or null; bot-only links left out), the site-wide breakdowns (top 10 named values plus `other`, as per link, `sources` included) and all-time `sum(url.visits)`; bio page views in range (`bioPageViews: {views, botViews}`, from `bio_page_daily_views`). Unique visitors are **per link per day, added up**: the visitor hash includes the link and the day, so no site-wide unique count exists, and one person on two links or on two days counts twice.
- **Links** (`url`, `url_tags`): links created per day stacked by `created_via` (the six values plus `unknown`); created in range: total, account, anonymous and tagged `ai`; now: total, active, inactive (total − active), expired (`expiration_date` before now, active or not), password-protected, with a visit limit, with an expiry date, and the blocked links by `block_reason`; the top 10 tags; the top 10 destination hosts of active links (`DomainNames.hostOf` in Java over every active `long_url`, fine at today's size); and the newest 10 links (`create_date` then id, descending, with owner and channel); dead destinations (`deadDestinations: {total, anonymous}`, active links with `destination_dead_since` set, the count the All URLs filter shows).
- **Users** (`user_account`, authorities, `api_key`, the OAuth tables): sign-ups per day stacked by sign-in method (`coalesce(auth_provider, 'local')`: `local`, `google`, `github`); now: total, active, deactivated (total − active), admins, email verified, 2FA on, and by provider; signed in within the last 7 and 30 days (`last_login`); API keys (`apiKeys: {active, expired, revoked, callsUsed}`): active (`active` and not expired), expired (whatever the flag) and revoked (switched off before it expired: `active = false` and `expiration_date` null or after `:today`), so the three add up to all keys, and the sum of `api_calls_used`. A key on its expiry day already counts as expired (`expiration_date <= :today` on the `DATE` column), as `DefaultApiKeyValidator` and `ApiKeyResponse` see it. Revoked includes keys switched off at their call limit (256 by default), which `ApiKeyResponse` shows as `LIMIT_REACHED`; MCP "connected now": the distinct `principal_name`s in `oauth2_authorization` with an access or refresh token unexpired at `:now` (current state, as the cleanup job prunes expired rows), and the count of `oauth2_registered_client`; bio pages (`bioPages: {total, hidden}`); notifications (`notifications: {consents, channels, autoDisabledChannels}`): active consent rows per `NotificationType` and channels per `ChannelType`, all seven and all five listed with zeros, and the channels turned off after failing (`enabled = false` with `auto_disabled_at` set).
- **Safety** (`link_review`, `url.block_reason` and `blocked_at`, `domain_rule`, the blocklist sources, `ScammerSignalService`): reviews opened per day as `SYSTEM` or `VISITOR` by the entry's current `system_flagged`; the open reviews and the visitor reports among them; reviews resolved in range by resolution, with the median and p90 minutes to resolve (nearest rank; null without resolved reviews; a negative time counts as 0); links blocked per day by `block_reason`, which counts links still blocked by their `blocked_at`, since unblocking clears it; the Block and Allow rule counts; the possible scammer count; and each source's name, action, enabled flag, entry count, memory, last success and last error. The last error is redacted: the source's own URL, fallbacks and last success URL (with and without the scheme) and then any other `http(s)://` address become `[url]`, because a source URL can carry an access key.
- **System**: the app version and JVM start time, uptime, Java version, active profiles and JVM heap; per redirect source (`cache`, `db`) the `redirect.duration` count, mean and max (count and mean since the last restart, Micrometer's max only over the last ~2 minutes; no percentiles are published); the `http.server.requests` count, all and `SERVER_ERROR`; the link cache's hits, misses and hit ratio (null without lookups); DB and Redis health; Redis used and max memory and the key counts; the database product, version as `major.minor` from `DatabaseMetaData` (for example `18.6`), size (`pg_database_size`, Postgres only, null on H2) and `shortUrlUnique` (see Unique short URLs); and emails per day by status (`SENT`, `FAILED`, `SENDING`, `RESENT`).
- **Health**: `HealthStatuses.status("db" | "redis")` asks `HealthEndpoint.healthForPath` through an `ObjectProvider`, not `HealthContributorRegistry`: with `reactor-core` on the classpath Boot registers the reactive `redisHealthContributor` and the blocking one backs off, so the blocking registry has no `redis`, while `HealthEndpoint` also consults the reactive one. A missing endpoint, a null result or any exception → `UNKNOWN`. When Redis is `DOWN` or `OUT_OF_SERVICE`, the System tab skips the Redis memory and key lookups (all three fields null) instead of waiting out more timeouts; with `UNKNOWN` it still tries, and each lookup is fail-soft (a failure → null and one warn line).
- **Redis keys** (`RedisKeyCounter`): `SCAN` in batches of 1,000, never `KEYS`, counting the prefixes `blocklist:`, `rate-limit:`, `analytics:`, `rdap:`, `dbl:`, `mcp:connect:` and `urls::` (the link cache), plus `other` (where the `digest:`, `burst:` and `public:` keys land) and `scanned`. It stops after 100,000 keys with `capped: true`, and the counts are then lower bounds.
- **Cache hit ratio**: `RedisCache.getStatistics()` of the `urls` cache, which needs the cache statistics on (see Cache Architecture).
- **App version** (`AppVersion`): `releases[0].version` of `src/main/resources/changelog.json` without its leading `v`, read once at startup; an unreadable file or a missing version → `unknown`. The public changelog is the version of record (`pom.xml` stays at 1.4.2), so the newest release there is the version the System tab and the Health page show.
- **Legacy `GET /api/v1/admin/stats`** keeps its JSON shape for the Health page and reuses `RuntimeMetrics`, `HealthStatuses` and `AppVersion`: `databaseActive` and `cacheActive` are true only for `UP`, the redirect average and max combine both sources, the cache hit ratio is a percentage or `—`, and `recentUrls` are the newest 10 links with their owners.
- **No IPs**: no stats query, response or log line holds an IP address, a User-Agent or a referrer URL; the stats come only from the daily analytics tables and entity counts. The one exception is the login-throttling panel on the stats page's System tab, the existing `GET /api/v1/admin/login-attempts` (IP → attempt count, in memory for a day), unchanged.

## Changelog
